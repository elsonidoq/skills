# Feature Specification: Model Family and Reasoning Effort Routing

**Feature Branch**: `main` (no branch hook registered; feature directory is independent)

**Created**: 2026-10-06

**Status**: Draft correction — least justified adequate effort, not risk-based overallocation; renewed current-content specification approval required before any downstream rubric/plan/task revision; settled recovery decisions unchanged

**Input**: User description: replace suite-wide planning and coordination model classes with independently selected model family and reasoning effort; use auditable provisional benchmark guidance, project-local experience, explicit Luna task contracts, and bounded, safely recovered retries. Only this specification and its quality checklist correction are authorized now; no implementation routing selection or dispatch is authorized.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Choose an Available Family and Effort (Priority: P1)

As the project owner, I can choose a model family and a separately justified reasoning effort for a planning stage, implementation task, or independent review, without old class tags constraining that choice or guessed runtime options being dispatched.

**Why this priority**: All downstream routing depends on a usable, explicitly authorized choice rather than a fixed class-to-provider mapping.

**Independent Test**: Present supported and unsupported family/effort combinations in a bounded workflow exercise; inspect the offered choices, recorded selection, and stop outcome without executing implementation work.

**Acceptance Scenarios**:

1. **Given** verified available bindings for Luna, Terra, Sol, and Astra with different supported efforts, **When** a family and effort are proposed, **Then** the advisory rubric evaluates family suitability separately from effort, only provider-documented and runtime-supported options may proceed to owner authorization, and task rationale, comparable benchmark signals, limitations, and uncertainty are recorded separately.
2. **Given** a configured family name but no verified usable binding or supported-effort evidence, **When** a stage requires that choice, **Then** it reports the exact capability gap and stops rather than inferring provider, version, effort, or a replacement model. **Given** an otherwise supported pairing without a qualifying benchmark row, **When** routing is considered, **Then** confidence is qualified and targeted research or an explicit owner decision addresses the gap; benchmark absence alone does not bar the pairing.
3. **Given** the Standard route and an owner-selected usable Sol binding for specification creation, **When** that stage is prepared, **Then** no fixed specification-class assignment overrides the selection; specification approval still precedes planning.
4. **Given** approved tasks with routing selections, **When** coordination groups sequential work or considers local execution, **Then** it preserves task dependencies, each task's family/effort contract, observed context limits, and authorization; it does not silently switch models to simplify execution.
5. **Given** future reviewed tasks, **When** final implementation approval is prepared, **Then** a per-task assignment table presents proposed family and independently justified effort, support evidence, rubric rationale, benchmark uncertainty, and bounded retry path before one final owner approval. Only approved assignments may subsequently pass execution preflight; specification correction does not select them.
6. **Given** a high-risk task has been decomposed, has a strong executable oracle, and a lower supported effort is justified as adequate for its remaining reasoning, **When** routing is proposed, **Then** risk strengthens applicable checks, rollback/approval/review safeguards rather than forcing high effort or the strongest family; the proposal selects the least supported effort justified as adequate.
7. **Given** a task has a weak oracle or unresolved acceptance ambiguity, **When** effort is proposed, **Then** it returns for decomposition and stronger observable acceptance rather than reflexively selecting max; any higher-effort proposal must identify a concrete reasoning need still remaining after that work or comparable evidence that lower effort is inadequate.
8. **Given** a fresh independent reviewer is required, **When** reviewer effort is proposed, **Then** the review's decomposed scope, remaining ambiguity, acceptance evidence, context and relevant comparable evidence determine the least supported effort justified as adequate; reviewer role, task stakes or available budget alone do not select high.

### User Story 2 - Obtain Auditable Initial Routing Guidance (Priority: P1)

As a planner, I can use credible, task-relevant benchmark findings as INITIAL provisional guidance, understand their limits, and find the original guidance again after project experience changes current guidelines.

**Why this priority**: Initial decisions must not masquerade as learned project evidence or rely on unsupported recollection about model capabilities.

**Independent Test**: Review a sample routing recommendation against its durable research record, then change the current project guideline and verify that a future agent can still locate the original recommendation, sources, applicability, and limitations.

**Acceptance Scenarios**:

1. **Given** consequential routing plan or task decisions are pending, **When** benchmark evidence is absent, insufficient, stale, or conflicting, **Then** planning completes targeted research or obtains an explicit owner decision acknowledging the uncertainty before the affected decision. Missing research capability or durable-write authority is reported, not replaced by invented results; an authorized uncertainty decision does not waive provider support, runtime capability, or owner routing gates.
2. **Given** inspected supplied CSVs or other task-relevant sources, **When** provisional guidance is proposed, **Then** each signal identifies the reported model/version, effort if reported, metric, direction, dataset/harness and test conditions, provenance and verification limits; unknown snapshot, reasoning mode, or evaluation date stays unknown and does not alone make an otherwise supported pairing ineligible.
3. **Given** a project later refines or supersedes a routing guideline, **When** an agent needs the initial rationale or supporting evidence, **Then** it can find the retained original guidance and relevant source record without reading the entire execution history.
4. **Given** two benchmarks use noncomparable versions, efforts, or test conditions, **When** routing is justified, **Then** the differences and uncertainty are visible; percentages from different benchmarks/harnesses, overlapping samples, and composites are not naively ranked, and no universal score threshold or promised success rate is asserted.
5. **Given** the owner prefers a more conservative per-task choice despite incomplete or mixed benchmark signals, **When** the proposal is recorded, **Then** it is labeled an owner preference with task rationale, not a synthetic measured score or permanent evidence-derived rule.
6. **Given** the raw supplied 369-row dataset is retained in a source-identified project-owned archive discoverable from compact research/index, **When** routine planning or implementation begins, **Then** agents receive concise rubric/citations without automatic whole-CSV loading or full-dataset task prompts. **When** a routing question needs source detail, **Then** agents can inspect matching rows on demand through that discovery link, without loading unrelated rows or inferring missing metadata.

### User Story 3 - Delegate a Deterministic Luna Task (Priority: P1)

As a coordinator, I can send eligible bounded implementation work to Luna only when its contract leaves exceptionally little unresolved implementation reasoning and provides an executable acceptance oracle.

**Why this priority**: Bounded execution is useful only when decomposition and observable acceptance protect correctness and reduce avoidable retries; comparative cost is verified, not inferred from family name.

**Independent Test**: Inspect one complete and one incomplete Luna-bound task; accept only the complete contract and demonstrate that its executable oracle distinguishes an incorrect outcome from the required one.

**Acceptance Scenarios**:

1. **Given** a candidate Luna task, **When** task readiness is checked, **Then** its objective, scope, allowed surfaces, exclusions, constraints, prerequisites, ordered steps, observable outputs, required capabilities, and executable pass/fail acceptance oracle are explicit before dispatch.
2. **Given** a task with an ambiguous outcome, missing producer, or an acceptance statement such as “looks correct” without an executable oracle, **When** Luna eligibility is assessed, **Then** dispatch is blocked until decomposition or task-contract correction resolves the defect; another family is not silently substituted.
3. **Given** several small dependent tasks, **When** they are prepared for delegation, **Then** each retains an independently verifiable outcome and checkpoint, producers precede consumers, and shared context does not turn them into one unbounded acceptance unit.

### User Story 4 - Recover a Failed Task Before a Bounded Retry (Priority: P1)

As the owner, I can understand a failed attempt, preserve its evidence, safely undo only its implementation commit before an authorized retry, and know that escalation will stop at the defined bound.

**Why this priority**: Retrying from contaminated task state or discarding unrelated work is unacceptable, even when a stronger family is available.

**Independent Test**: Use isolated task-state examples with a failed task commit, unrelated changes, and dependent work; inspect diagnosis, pre-mutation evidence, recovery result, attempt count, and stop outcomes. These examples do not authorize rollback in a real project.

**Acceptance Scenarios**:

1. **Given** an eligible Luna task fails with wholly task-owned changes, **When** failure inspection and pre-mutation evidence establish safe recovery, **Then** an existing task-only implementation commit is used, or a focused failed-attempt commit is created even if required checks failed; it is explicitly marked NOT VERIFIED, ordinarily reverted by a separate inverse commit, and the restored starting state is checked before an authorized Terra attempt. A failed Terra attempt can similarly reach Sol, but a failed Sol attempt stops. The task has at most three total attempts.
2. **Given** a task starts on Terra, **When** Terra fails and retry prerequisites pass, **Then** only Sol is the automatic next-family candidate; after Sol fails the task stops. **Given** a task starts on Sol, **When** it fails, **Then** it stops after that single attempt absent a new owner decision.
3. **Given** failure inspection identifies unavailable tools, permissions, runtime capability, or another environmental cause, **When** escalation is considered, **Then** that cause is distinguished from reasoning failure and must be resolved under existing authority before another attempt; a different family or higher effort is not assumed to repair the environment.
4. **Given** mixed-ownership commits, baseline drift, dependent work that would be invalidated, unavailable failure details, or an unproven task-only inverse, **When** recovery is considered, **Then** mutation and retry stop with the exact blocker; unrelated changes and recorded evidence remain intact.
5. **Given** an inspected diagnosed failure permits the next family in the bounded sequence, **When** retry effort is proposed, **Then** it is independently justified from that binding's verified supported options and receives separate explicit owner approval before retry. Neither the family sequence nor rollback preauthorization approves effort escalation; no automatic increment, fixed ladder or unsupported request is used.
6. **Given** all allowed attempts have failed, **When** Astra is available, **Then** availability does not authorize a fourth attempt; a new owner decision is required for any further execution.

### User Story 5 - Learn Without Rewriting Project Policy Automatically (Priority: P2)

As the project owner, I can review factual routing outcomes separately from proposed reusable guidelines, retain useful initial evidence, and approve, edit, reject, or add guidance without weakening existing approvals or review.

**Why this priority**: Evidence should improve future coordination while preserving uncertainty, project boundaries, and owner control.

**Independent Test**: Record success, failure, and recovery in separate indexed task/run evidence; propose a guideline change and exercise rejection, exact-content approval, and concurrent drift. Verify only approved, baseline-matching guidance changes persist.

**Acceptance Scenarios**:

1. **Given** a failed and retried task, **When** its checkpoint is recorded, **Then** each attempt has its own family/binding/effort, baseline and result or unknown status, checks, diagnosis, invocation/run references, recovery evidence, and outcome; the compact project-local index points to the relevant records rather than reproducing logs.
2. **Given** one Luna failure, **When** reflection proposes guidance, **Then** it retains uncertainty and counterevidence and does not impose a permanent family/subsystem ban or silently alter synthesized guidelines.
3. **Given** rejected or pending guidance, **When** the run closes, **Then** guideline bytes remain unchanged, the disposition and evidence remain discoverable, and implementation acceptance is reported separately from guideline approval.
4. **Given** approved guideline content whose baseline has changed before application, **When** persistence is attempted, **Then** application stops for renewed owner review rather than overwriting concurrent edits.
5. **Given** existing TinySpec, Standard, or documented legacy artifacts, **When** work resumes, **Then** valid provenance and approval evidence are retained, unresolved routing is explicitly selected and verified, and no historical approval, model mapping, or planning-depth choice is fabricated.

### Edge Cases

- A verified option disappears between owner selection and dispatch: stop and seek an authorized replacement; configuration names and past successful launches alone are not current capability proof.
- A family exposes one effort or no adjustable effort: record the verified supported behavior explicitly; do not invent an effort menu or equate omitted effort with a known value.
- A failed launch has uncertain execution status: preserve the uncertainty and stop; do not infer success, a safe clean state, or a refunded attempt.
- A failed invocation is resumed, rotated, or placed in another batch: renewed task execution after failure is another attempt and must follow the same remaining family sequence; renaming or session changes never reset the budget.
- A failure produced no implementation commit: record the failure and verify task baseline, ownership, and partial changes. If wholly task-owned changes exist and are safe to checkpoint, make an explicitly failed-attempt commit followed by its ordinary inverse; if nothing changed, or safe task-only commit/revert is unavailable, stop retry without an empty or fabricated commit.
- A defect is found after dependents have consumed a committed task: stop retry/rollback, inspect dependency impact, and return unsafe recovery or changed scope to the owner; do not automatically undo downstream work.
- A recovery, evidence write, checkpoint, or required check fails: report the exact blocker and stop affected execution, leaving recoverable state and evidence intact.
- Astra may be explicitly selected for an initial stage, review, or task when verified and authorized; it is outside the automatic implementation retry sequence. An initial Astra task failure has no automatic next attempt.
- An empty project guideline store supplies no learned routing rules. No matching history supplies no invented evidence; mandatory coordination persistence still applies.
- Benchmarks omit a family, specific snapshot, supported effort, or relevant workload: retain the coverage gap, lower confidence in benchmark-derived recommendations, and trigger targeted research or an explicit owner uncertainty decision; do not automatically exclude an otherwise provider-documented, runtime-supported, owner-authorized pairing.
- Supplied effort rows and model catalogs are not callability proof; collection dates are not evaluation dates, current methodology is not a per-row execution manifest, and effort labels do not disclose an unspecified reasoning mode.
- Terminal-Bench 4.0 AA rows with a 66-task, three-repeat mini-swe-agent setup are distinct from the previously inspected 330-trial public leaderboard in `research.md`; Terminal-Bench 2.1, 3.0, Hard, and Science variants also remain distinct. Same-name metrics do not establish matched harnesses or comparable runs.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The suite MUST replace `sonnet-class`/`opus-class` model specification throughout active planning and coordination workflows with model family and independently selected reasoning effort. This includes stage assignments, task contracts, delegation briefs, recovery rules, adapters/direct consumers, validation expectations, and normative documentation/configuration examples. Neither obsolete tags nor class-share rules may remain active routing authority under another spelling.
- **FR-002**: Initial family names MUST be Luna, Terra, Sol, and Astra. A family name MUST NOT imply a provider, concrete model version, capability, price, context size, or supported effort. The permitted runtime binding and its supported options MUST be verified when needed; not every family supports every effort.
- **FR-003**: Each stage/task/review routing proposal MUST identify family, verified concrete binding, independently justified supported effort or explicitly verified nonadjustable behavior, provider-documentation and runtime capability evidence, task/rubric rationale, available benchmark signals and coverage gaps, uncertainty, and owner authorization before execution. Benchmark coverage is advisory, not a configuration-eligibility gate: absence of a qualifying row alone MUST NOT bar an otherwise supported pairing. Unobserved actual execution details MUST be recorded as unknown, not inferred from a requested setting.
- **FR-004**: Only permitted, usable options MUST be offered. Missing question, delegation, independent-review, mutation-tool, or other required capabilities MUST stop the affected stage with an exact capability report. Model availability checks MUST NOT install dependencies or grant external-operation authority.
- **FR-005**: Routing guidance MUST use the advisory family/effort rubric below, evaluating family suitability against task characteristics, context/tool demands, relevant local outcomes and comparable evidence. Risk/criticality MUST be addressed through stronger decomposition, executable checks and applicable rollback/approval/review safeguards, not treated as a proxy for residual reasoning or an automatic reason for higher effort or the strongest family. Effort MUST be justified separately under FR-013 after decomposition. A family MUST NOT have a permanently fixed effort, stage, or universal capability ranking; no universal score threshold or automatic maximum-effort rule is permitted. Source requirements and owner-selected routing remain authoritative.
- **FR-006**: Before consequential routing plan/task decisions, planning MUST inspect adequate relevant evidence or complete targeted research under the existing dependency-research contract. Insufficient applicability, conflicting/missing evidence, research capabilities, or durable-write authority MUST be reported and trigger targeted research or an explicit bounded owner decision acknowledging uncertainty, allowed scope, and remaining validation before the affected decision. Such an owner decision may allow an otherwise supported pairing without a qualifying benchmark row; it MUST NOT fabricate coverage or waive provider-documentation, runtime-support, routing-authorization, or REQUIRED acceptance gates.
- **FR-007**: INITIAL provisional guidance MUST use credible inspected coding/tool-use or other task-relevant signals, preferring primary reports and reproducible methodology where available. Each signal MUST retain source identity/location and supporting row/span, inspection date, reported provider/model/version and effort if available, metric/unit/direction, dataset/split/harness and test conditions, result as reported, source/verification status, limitations, and task applicability. Missing evaluation date, exact snapshot, reasoning mode, or run manifest MUST remain explicit uncertainty, not automatic ineligibility. Secondary verification labels MUST NOT be upgraded to firsthand primary verification; other versions/efforts and estimated aggregates may supply qualified context, not invented exact-pair measurements.
- **FR-008**: Benchmark observations, derived provisional recommendations, owner decisions, and project execution outcomes MUST be distinguishable. Cross-family or within-family effort comparisons MUST establish comparable benchmark/version, metric/direction, split, harness, and setup and retain remaining uncertainty; percentages from different benchmarks/harnesses MUST NOT be naively ranked. Composite indices, normalized Elo, overlapping samples, unknown snapshots, missing dates, and counterevidence MUST be qualified. An external score alone MUST NOT guarantee a project's outcome; a conservative owner preference MUST be labeled a choice, never a synthetic measured score.
- **FR-009**: The original benchmark-informed guidance and supporting provenance MUST remain durably discoverable for future agents whenever relevant, including after project guidelines are edited, superseded, or removed. Normal guideline maintenance MUST NOT erase that baseline or its sources. Future approved planning MUST retain a project-owned archive of the raw supplied 369-row CSV, preserving its source identity and digest, with discoverability from compact research/index. Routine planning and implementation agents MUST receive concise rubric/citations only, not automatically load the whole CSV or receive the full dataset copied into task prompts. Agents MUST retain on-demand access for selective matching-row inspection through that discovery link; missing metadata MUST remain unknown, never silently inferred. Retrieval MUST allow relevant-only access without loading all execution history; current guidance and retained initial guidance MUST be clearly distinguished.
- **FR-010**: Global assets MUST contain reusable routing process only, not any project's learned outcomes or permanent project-specific policy. Factual attempts and project-specific synthesis MUST remain in the existing project-local coordination stores and their compact index, separate from gotcha memory and durable benchmark reference material.
- **FR-011**: All implementation tasks MUST remain decomposition-friendly and independently verifiable, with explicit prerequisites and source traceability. Routing MUST NOT replace clear task boundaries, producer-before-consumer ordering, or acceptance checkpoints.
- **FR-012**: Luna-bound implementation tasks MUST have an exceptionally explicit objective, scope and allowed surfaces, exclusions, constraints, dependencies, ordered steps with observable outputs, required capabilities, and executable acceptance oracle with a deterministic pass/fail result. Missing or ambiguous elements MUST block Luna dispatch and return to task preparation/review; no informal assurance substitutes for the oracle.
- **FR-013**: Family and effort choices MUST remain separate from approval of task scope and acceptance. For every stage/task and independent review, effort MUST be the least reasoning effort among the selected binding's verified supported settings justified as adequate after decomposition, considering residual ambiguity/reasoning need, oracle quality, task-specific comparable evidence and context/latency/cost constraints. Higher effort MUST cite a concrete remaining reasoning need or comparable counterevidence that a lower setting is inadequate; role label, family name, stakes alone or available budget MUST NOT substitute. Weak-oracle work MUST prompt decomposition and stronger observable acceptance before an effort proposal, not reflexive max. No unconditional low/medium default, mandatory probe for every configuration, fabricated savings or unverified price claim is permitted; evidence gaps follow FR-006. Retry effort selection MUST follow inspected diagnosed failure and separate explicit owner approval, distinct from the approved family sequence and rollback preauthorization. There MUST NOT be a fixed effort escalation ladder or automatic increase after failure.
- **FR-014**: Automatic implementation retry candidates MUST follow eligible Luna → Terra → Sol, starting Terra → Sol, or starting Sol → stop. The maximum is THREE total task attempts, including the initial attempt; the starting family reduces the available sequence to two or one respectively. Each automatic candidate still requires safe recovery, verified capabilities, existing owner-selected routing authority, and unchanged applicable approvals. No automatic Astra fourth attempt or skipping an unavailable next family is allowed.
- **FR-015**: An attempt MUST cover actual task execution, not approval dialogue or a read-only preflight. Every renewed task execution after failure, including resume/relaunch, MUST consume the next permitted attempt; session, batch, model-version, or effort changes MUST NOT reset or extend the count. Uncertain execution status MUST stop for inspection rather than create an assumed extra allowance. Further execution outside the sequence requires a new explicit owner decision, recorded separately from the exhausted automatic budget.
- **FR-016**: Before retry or recovery, the coordinator MUST inspect the failed run/session and failed tool invocation, review task checks and any commit/partial changes, and distinguish reasoning/implementation failure from capability/environment failure or unknown cause. The diagnosis, proposed corrective action, and why another attempt could address the cause MUST be recorded. Unknown cause or unavailable inspection evidence MUST stop; an environment failure MUST NOT automatically justify stronger reasoning.
- **FR-017**: After a failed attempt with wholly task-owned changes, the coordinator MUST identify its existing implementation commit or create one focused commit of those failed changes, even when required checks failed. Such a new commit MUST be identified as a FAILED-ATTEMPT checkpoint, never a verified task completion or release of dependents. Before retry, the failed task commit MUST be undone by a separate ordinary history-preserving inverse commit; no alternate inverse, reset, history rewrite, unrelated-work discard, evidence undo, or automatic dependent-task revert is allowed. If nothing changed or a safe commit-and-inverse pair cannot be made, record the failure and stop retry; never create empty or fabricated commits.
- **FR-018**: Before a failed-attempt commit or inverse, recovery eligibility MUST establish the failed attempt's baseline, exact owned paths/changes, existing or proposed task commit, current index/worktree and approval state, required-check results, and dependent-task impact. Mixed ownership, unsafe or sensitive content, conflicting changes, unverified baseline, invalidated dependencies, or unavailable ordinary task-only inverse MUST stop mutation and retry. A whole-project clean tree MUST NOT be obtained by erasing unrelated work.
- **FR-019**: Failure, diagnosis, existing commit identity or proposed failed-attempt commit scope, ordinary inverse scope, safety/dependency assessment, and applicable recovery authorization MUST be persisted and checkpointed in project-local evidence BEFORE either recovery commit. Record the failure commit identity and its failed-check status before the inverse; after recovery, evidence MUST record both commit identities, actual inverse result, restoration checks, and preserved unrelated state. Persistence/checkpoint failures MUST stop before the next mutation or dispatch.
- **FR-020**: Successful recovery MUST leave a verified task starting state, an auditable failed-task commit and distinct ordinary inverse commit, and separately retained failure/rollback evidence before another attempt. Approval of the current feature/task recovery policy preauthorizes only demonstrably safe task-only failed-attempt and inverse commits within its recorded bounds; no routine per-inverse owner question is needed. Unsafe, unclear, or out-of-bounds recovery stops for an explicit owner decision; ordinary implementation approval alone does not grant rollback authority before this policy is approved.
- **FR-021**: Every attempt/checkpoint MUST record task/run identity, characteristics and optional residual-reasoning rationale, selected and observed family/binding/effort, attempt number and remaining budget, baseline/result revision or explicit absence, inspection/diagnosis, required check outcomes, reviewer/manual findings, recovery, escalation, and final disposition. Failed, blocked, partial, and unknown outcomes MUST remain factual and attributable.
- **FR-022**: Growing execution evidence MUST remain separate run/task records with a compact index. Record creation/update MUST precede index refresh; interrupted updates MUST be reconciled. Ordinary planning MUST read compact project guidelines first, not all history; justified historical retrieval MUST be index-first and relevant-only. Sensitive payloads, credentials, and personal data MUST NOT be persisted.
- **FR-023**: Reflection MUST distinguish direct observations, tentative/repeated patterns, stable guidance, insufficient evidence, and contradictions. One failure MUST NOT become a permanent routing rule. Candidate add/refine/supersede/remove changes MUST be separated from factual evidence and linked to supporting and contradicting sources, including retained initial guidance where relevant.
- **FR-024**: Synthesized project guideline changes MUST require explicit owner accept/edit/reject/add review of exact resulting content, independently of implementation approval. Pending, rejected, cancelled, ambiguous, or unavailable approval MUST leave guideline bytes unchanged. Current-content drift MUST stop application and require renewed review; approved changes MUST NOT erase retained benchmark provenance.
- **FR-025**: TinySpec and Standard depth choice, current-content source/specification/final approval gates, dependency order, execution authorization, sequential coordination, per-task implementation and distinct evidence checkpoints, required acceptance checks, and fresh independent final review MUST be preserved. Before one final owner implementation approval, future reviewed tasks MUST have an assignment table with proposed per-task family, independent effort, support evidence, rubric rationale/uncertainty, and bounded retry path; that approval covers assignments together with the reviewed implementation scope, not an automatic dispatch waiver. Family/effort changes MUST NOT weaken these boundaries or bypass a missing reviewer. This material correction MUST receive renewed current-content specification approval before any plan/task revision; older approved digests and benchmark-only downstream assertions are not authority for the corrected content.
- **FR-026**: Existing and documented legacy artifacts MUST retain valid shapes, provenance, evidence, and approval history where compatible. Historical class labels MUST NOT be interpreted as current family/effort authority or converted into guessed mappings. Resumed execution requiring new routing selection or materially changed contracts MUST return to the affected owner gate; no forced recreation or fabricated approval is permitted.
- **FR-027**: Future feature verification MUST cover supported/unsupported selections, advisory missing-row handling, independent family/effort rationale, high-risk/strong-oracle non-escalation, weak-oracle decomposition, reviewer effort without role-based high defaults, diagnosed and separately approved retry effort, noncomparable-score and owner-preference treatment, assignment-table-before-final-approval ordering, all three bounded retry starts, no automatic Astra continuation, failure-cause inspection, safe and blocked recovery, incomplete Luna contracts, evidence/index persistence, selective retrieval, rejected/approved/drifted guideline changes, retained initial guidance, and both workflow routes with legacy recovery. Static/isolated demonstrations MUST NOT be reported as live model-obedience or real benchmark proof.

### Advisory Family/Effort Rubric

The rubric produces an auditable proposal, not a measured suitability score or automatic assignment (FR-003–FR-008, FR-012–FR-013, FR-025):

- **Task profile**: Decompose the work and distinguish risk of incorrect/irreversible changes and security/data/dependency impact from reasoning that remains unresolved: ambiguity, novelty, interacting constraints and required judgments. Risk drives applicable decomposition, executable checks, rollback/approval/review safeguards, not an automatic family/effort upgrade. Assess oracle quality and context/tool needs separately. Missing price, latency or context evidence stays unknown; no fabricated savings or unverified price assumption supplies a rationale.
- **Family suitability**: Evaluate supported family alternatives against the decomposed task's characteristics, context/tool requirements and relevant comparable/local evidence. Task complexity or criticality alone does not choose the strongest family; a proposal explains specific suitability and remaining uncertainty. For Luna, the complete deterministic brief and oracle in FR-012 are mandatory regardless of benchmark score. Terra, Sol and Astra are not automatically ranked by name; no family removes REQUIRED checks or owner gates.
- **Benchmark signals**: Prefer task-relevant coding/tool-use evidence over unrelated or composite scores. Compare only sufficiently matched benchmark versions, splits, metrics and harness/setup conditions; explain how the signal informs the specific task and retain remaining uncertainty. Coverage across all reported efforts in the supplied data broadens context, not proof of exact-snapshot equivalence, runtime support, or project-task success.
- **Independent effort proposal**: For the proposed family/binding, select the least provider-documented, runtime-supported effort justified as adequate after decomposition, using residual ambiguity/reasoning, oracle quality, task-specific comparable evidence and context/latency/cost constraints. Higher effort requires a concrete remaining reasoning need or counterevidence that a lower setting is inadequate; stakes, role (including independent reviewer), family name or spare budget alone are not justification. A weak oracle calls for decomposition/stronger observable acceptance, not reflexive max. There is no unconditional low/medium default or mandatory per-configuration probe. The supplied data contain nonmonotonic results; more effort is not assumed better, and another family's effort label or family-level score cannot supply an exact effort result. After failure, retry effort requires an inspected diagnosis and separate owner approval, not an automatic increment within the Luna → Terra → Sol sequence.
- **Uncertainty and owner choice**: Identify missing/noncomparable signals and verification limits; qualify confidence without fabricated numeric scoring. Targeted research or an explicit owner uncertainty decision must address consequential gaps. A conservative family/effort preference is recorded as an owner choice with rationale, not a measured benchmark advantage. Support/callability and authorization remain hard gates even when benchmark confidence is high.
- **Approval outcome**: Future proposals belong in the reviewed per-task assignment table before one final owner implementation approval. Preserve independent family/effort rationale, evidence/gaps, acceptance and bounded retry policy; no table, model selection, or dispatch is produced in this correction.

### Key Entities *(include if feature involves data)*

- **Model family**: Luna, Terra, Sol, or Astra; an owner-facing routing identity, distinct from its currently verified provider/model binding and from effort.
- **Runtime capability observation**: Permitted usable binding, supported effort behavior, relevant tools/context/delegation limits, verification evidence and applicability to the imminent stage.
- **Routing proposal/selection**: Stage/task/reviewer identity, family and concrete binding, independently justified effort, task profile, support evidence, advisory benchmark signals/uncertainty, and current owner authority; future task proposals are reviewed together in the assignment table before final approval.
- **Initial routing guidance and benchmark record**: Retained provisional recommendation and inspected supporting claims, tested versions/efforts/conditions, limitations, provenance and discovery references; distinct from evolving project guidelines.
- **Task contract and attempt**: Bounded outcome, dependencies, acceptance oracle and routing; each attributable execution attempt has its own checks, diagnosis, revision, count and disposition.
- **Recovery assessment and result**: Failed task baseline/commit/ownership, dependency impact, proposed inverse scope, approval evidence, pre-mutation checkpoint and verified post-recovery state.
- **Project coordination evidence and guidelines**: Separate indexed factual run/task records and compact mutable project guidance, connected through owner-reviewed reflection rather than automatic promotion.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Across all active planning/coordination entry points and normative routing examples, zero obsolete class-based routing instructions remain; every proposal separately justifies family and the least supported effort adequate after decomposition, and every unsupported or unauthorized option is blocked. High-risk/strong-oracle, weak-oracle and independent-review examples produce zero automatic high/max or strongest-family choices from stakes, role, family name or budget alone; weak-oracle examples return for decomposition/stronger acceptance, and every higher-effort proposal identifies a concrete remaining reasoning need or comparable lower-setting counterevidence. A supported-pairing example with no qualifying benchmark row is not rejected solely for absence: it records uncertainty and research or an explicit owner decision (FR-001–FR-007, FR-013, FR-025–FR-026).
- **SC-002**: Every consequential initial routing recommendation exposes its supporting signals, comparability and missing-data limits or an explicit bounded owner uncertainty decision; zero examples naively rank noncomparable percentages or convert an owner preference into a measured score. A future agent can recover the original recommendation and provenance after a current guideline is superseded without opening unrelated run records. Routine planning/implementation examples produce zero automatic whole-CSV loads or full-dataset task prompts; an on-demand lookup resolves compact research/index → source-identified project archive → matching rows only, preserving unknown metadata (FR-006–FR-010).
- **SC-003**: Every Luna-bound implementation task in acceptance examples exposes all required contract elements and an executable oracle; each incomplete example is blocked before dispatch (FR-011–FR-012).
- **SC-004**: Failed-task examples starting on Luna, Terra, and Sol permit no more than three, two, and one total attempts respectively; zero automatic Astra fourth attempts occur. Retry effort proposals require inspected diagnosis and separate explicit owner approval, with zero automatic effort increments; missing inspection, effort authorization or recovery evidence blocks renewed execution (FR-013–FR-016).
