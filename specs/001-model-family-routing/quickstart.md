# Model routing — validation guide (plan stage)

This is a proposed acceptance guide, **not evidence that the routing change is implemented**. Source: [approved spec](spec.md), [plan](plan.md), [benchmark record](research.md). Tests of prompt text and simulated Git state cannot prove live model obedience, benchmark generalization, or provider effort support.

## Preconditions

- Work from a reviewed, approved implementation task list and a known Git baseline. Preserve unrelated untracked/staged files. The currently present `.env` is unrelated and may contain secrets: do not stage, print or copy it into evidence.
- `python3`, Git and the repository's existing checker scripts are available; report `UNAVAILABLE` honestly if not. User question/delegation/model capabilities are verified at the stage using them, not inferred from a file or a cached listing.
- Before the single final implementation approval, present every task and the independent reviewer with proposed family, exact binding, independently justified effort, task risk/complexity/oracle/context/cost profile, provider/runtime evidence, comparable advisory signals, gaps and uncertainty disposition. Let the owner ask for changes before approving scope and listed assignments together; an absent proposal or unsupported/unverified runtime/effort is **non-dispatchable**, never silently substituted. Benchmark absence alone does not block a supported pairing: targeted research or an explicit bounded owner uncertainty decision addresses the gap before consequential selection. Current [task proposals](tasks.md) are not selections until that approval. At dispatch, recheck current scope/capability/evidence and stop for renewed owner decision on drift rather than silently substitute.

## Focused checks after the approved implementation exists

1. **Routing contract:** in-memory instruction mutations must fail when a planner stage retains an obsolete `sonnet-class`/`opus-class` tag, when owner choice/usable capability is removed, when a supported no-row pairing is rejected solely for benchmark absence, when an Estimated/other-version row is fabricated as an exact-pair measurement, when unresolved uncertainty is hidden, when noncomparable harness percentages become ordering, or when an owner preference becomes a synthetic suitability score. Family and effort need separate task-sensitive rationale: after decomposition choose the least supported effort justified as adequate; a higher setting needs concrete remaining reasoning or comparable lower-setting counterevidence. Negative fixtures must reject risk/role/available-budget ⇒ high or strongest-family shortcuts, weak-oracle ⇒ reflexive max (return for stronger acceptance), unconditional low/medium defaults, and invented cost savings. A fixed family effort or automatic max rule fails. Test that an incomplete pre-approval task/reviewer assignment preview blocks final approval readiness, that one final answer approves both distinct scope and assignment records, and that any changed approved assignment stops before dispatch rather than producing a routine second question or silent substitution. Verify staged choices preserve TinySpec/Standard approvals, reviewer independence, and legacy content without fabricated mappings.
2. **Effort matrix boundaries:** with fixture rows for Luna, Terra, Sol and Astra and differing supported effort sets, only **provider-documented permitted usable runtime/effort** choices are offered as usable. Include unsupported effort, unavailable modelScope and stale binding hard-stop cases; also no reported effort, different version, missing/irrelevant benchmark, unknown snapshot/mode/date and conflicting evidence advisory cases. A supported pairing with no row passes the coverage boundary after research or explicit bounded owner uncertainty decision, never by fabricating coverage or waiving other gates. Show within-family nonmonotonic results and qualified comparability; no score threshold or universal rank. Fixture numbers are labelled simulated; no fabricated real-world ranking.
3. **Luna clarity:** a complete bounded task has exact inputs/allowed files, prerequisites, ordered steps, observable outputs and an executable acceptance check that demonstrably rejects a wrong result. Missing any one of these blocks Luna assignment before dispatch; do not silently substitute another family or waive required acceptance.
4. **Budget/escalation:** demonstrate starting Luna allows at most Luna → Terra → Sol, starting Terra at most Terra → Sol, starting Sol one attempt, and Astra no automatic successor. Resumed/rotated runs count as new attempts after failed execution. Missing next-family runtime/effort support, routing permission, verified task starting state or diagnosed cause blocks before retry; advisory gaps need research or owner uncertainty disposition and are not automatic missing-row exclusion; environment failure alone does not advance to a stronger reasoner. After diagnosis, an independently justified least adequate supported retry effort inside existing owner-selected routing authority may proceed without a routine second approval; an out-of-authority family/effort, changed scope or unclear safety/capability stops for renewed owner choice. Reject preselected effort before diagnosis, automatic increments and a blanket per-retry question.
5. **Temporary-Git recovery fixtures:** create clean temporary repositories, with unrelated staged/unstaged paths and one task-owned failing diff. Check failure evidence written **and committed before mutation**, failed-attempt commit (NOT VERIFIED) even when required checks failed, distinct ordinary inverse commit, restoration check and separately checkpointed result evidence before another attempt. Also test a previously verified implementation commit that later fails review, a commit hook failure, no changes, mixed ownership, index drift, inverse conflict, already-consumed dependencies and sensitive content. Each unsafe case must stop without reset, hidden cleanup, empty commits or losing unrelated changes. Keep real project worktree out of fixture mutations.
6. **Learning/discovery:** after simulated guideline supersession/removal, resolve `docs/index.md` → compact research/rubric → source-identified project-owned 369-row archive → matching rows only; verify original digest/bytes and unknown metadata. Instrument fixture reads/prompts: routine planning/implementation must produce zero automatic whole-CSV loads or full-dataset prompts; on-demand lookup returns the requested family/effort/benchmark only, not unrelated run history. Failed/blocked outcomes remain separate indexed project evidence; rejection/pending/drifted approval keeps guideline bytes identical; exact-content approval applies only baseline-matching content. A single failure never creates an automatic routing ban.
7. **Integration and claims:** run focused planner/coordination/task-generation contract/mutation tests, `bash scripts/check-skills-lint.sh`, relevant suite scripts, and `git diff --check` from repo root. Inspect the actual diff and scripts that enforce the new invariant; static PASS is only instruction/fixture evidence. Run real model/effort/provider checks solely with separate permission, capturing exact requested/observed binding and behavior; report NOT RUN otherwise. Inspect independent final review against current approved spec/plan/tasks before implementation acceptance.

## Expected output

A compact table per check with `PASS`, `FAIL`, `NOT RUN`, or `UNAVAILABLE`, exact command/evidence path and the scope that result covers. No benchmark score, family rank, configuration availability, rollback safety or user approval is inferred from static assertions alone.
