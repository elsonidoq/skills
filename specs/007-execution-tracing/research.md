## Evidence, decisions, alternatives and observable checks

### R1 — Reuse ordered history and the existing graph

**Repository evidence:** [store.py](../../runtime/coherence_workflow/store.py), `Store.thread_connection`, lines 152–168, gives each graph worker a connection and forbids transactions across SDK calls/waits. Lines 178–204 define `execution_run_inputs`, ordered `execution_history(seq, run_id, task_id, kind, state, details, recorded_at)` and separate review execution/attempt rows. `history` (420–434) appends rather than replaces failures. `graph.py` `worker`, `wait`, `checks`, `checkpoint` (249–521) already retain invocation IDs, waiting tool-call identity, worker summaries, actual command/exit/output and commit/correction relations. `_run_graph` (730–801) already supplies synchronous durable interrupt/resume and success/error boundaries. [Schema owner](../../docs/coordinate-implementation-schema.md#public-graph-execution-boundary) agrees; stale target language in AGENTS is not a rewrite prerequisite.

**Dependency provenance:** `runtime/pyproject.toml` declares Python >=3.10, LangGraph 1.2.21 and langgraph-checkpoint-sqlite 3.1.3. Local `importlib.metadata.version` returned these same graph versions. No dependency changes are proposed. Existing production calls and graph tests provide sufficient evidence for reusing this integration; no new graph API or internet lifecycle claim is needed.

**Decision:** add factual question/coverage/publication event kinds in existing history; join existing outcome/check/review records instead of mirroring all of them. Version the new details payload, not the database. Treat graph checkpoints as control state, not delivery proof. Use current short transactions and the inherited writer lock. New optional capture errors report coverage loss without changing implementation validity; do not weaken existing required history used for effect safety.

**Alternatives:** new trace DB, graph rewrite, SQL migration or full transcript ingestion add no necessary capability. Reconstructing answers from prompts alone cannot establish complete capture. Public `status` is intentionally lossy, not an export source.

**Check:** exercise actual history reader and capture helper against two attempts, rejection, check failure/pass, question/resolution and reopen. Verify old rows remain byte-equivalent and absent new coverage is unknown, not zero. Directed-wave fixture must pair by IDs despite interleaving; no SQLite transaction spans a question or network call.

### R2 — Capture actual questions at tool boundaries, not metadata broadcasts

**Repository evidence:** [host.mjs](../../runtime/pi-host/host.mjs), `ask_owner` at 175–195, retains `tool_call_id` in paused questions, but its non-paused callback currently sends only text. [pi_adapter.py](../../runtime/coherence_workflow/pi_adapter.py) `prompt.callback` calls `observe_question` with state strings only. `parent_question` uses run/session/request correlation but returns only answer text. [Bridge](../../runtime/pi-extensions/coordinate-implementation-bridge.js), `showNextQuestion` and the two reply tools, distinguishes coordinator triage from owner-only reply. It does not itself observe the actual `ask_user` result. [graph.py](../../runtime/coherence_workflow/graph.py) `answer_graph_question` calls a question function with text, then binds the answer to the paused invocation. This is useful context, not complete factual owner capture.

**Installed dependency source (inspected, not a version mandate):** the production SDK loader resolved `/usr/local/lib/node_modules/@earendil-works/pi-coding-agent`, version **1.4.0**. `runtime/pi-host/package.json` names **0.87.1** as installation metadata; these are not claimed equal. Installed `dist/core/extensions/types.d.ts`, lines 931–1039, defines `tool_call` and `tool_result`, both with `toolCallId`, tool name and input; custom result has `details: unknown`, content and `isError`. Existing host code already uses these hooks. Installed `/opt/pi-packages/node_modules/pi-ask-user` is **0.15.1**, source `index.ts` 2160–2179: full event broadcasts are disabled by default and `ask:answered` sends only response kind. Lines 2338–2354 return actual question/context/options/response/cancelled in normal tool-result `details`. Source repository: https://github.com/edlsh/pi-ask-user . These supporting spans establish hook inputs, not live hook ordering or model obedience.

**Decision:** observe the normal `ask_user` call/result in the existing parent bridge, only for its active run. Retain tool-call identity and actual response selections/freeform/comment, question/options/context needed to understand the answer, errors and cancellation. Do not enable global full-event broadcasts, install an extension, change ask_user, or publish unrelated session conversation. Capture worker/coordinator request and reply separately. An owner question during triage is an owner event; the returned worker resolution is a separate event. Never infer that their texts are identical or that a coordinator reply is owner consent. Keep explicit request/parent links when actually known; otherwise mark linkage unavailable.

Extend existing private bridge request/reply transport to convey captured facts to the runner, including an evidence-drain request at finish/error before bridge teardown. Persist incoming facts in existing history. Pending question replies carry their observed owner events automatically; other in-flight owner events are drained at the next boundary. Stable event IDs allow a retained batch to be re-read without double counts. Keep the parent buffer until the runner acknowledges persistence, and retain capture failure/gaps. No coordinator-authored log or extra agent call. Abrupt parent/process death can lose an unacknowledged buffer; report that coverage gap, recover only actually retained current-run facts when available, never invent completeness.

**Alternatives:** listening to `ask:answered` loses actual answers; asking the coordinator to transcribe them violates automatic capture; changing shared broadcast privacy exposes unrelated extensions. A second recorder service or direct competing SQLite writer is unnecessary.

**Earliest check:** extend `test_question_triage.mjs`, `test_bridge.mjs`, `test_pi_adapter.py` and `test_graph_questions.py` at actual hooks/transport. Use distinct owner wording and coordinator resolution, cancelled result, missing result, reply failure, two IDs, paused reopen and terminal drain. Test the installed SDK hook path without provider use before downstream formatter reliance. Live representative execution remains separately required.

### R3 — Capture meaningful outcomes without inventing acceptance

**Repository evidence:** `engine.py` `_prompt_worker` (288–306) rejects explicit unsuccessful outcomes; `_review_worker_evidence` (918–941) includes completed summaries only. Graph worker-return history retains the submitted summary before runner checks. Fixer-return history at 497–505 currently retains effects but **not** its returned summary. `_review_impl` retains findings, coverage gaps and reviewed range in review attempts. `verification.py` `_run_check` / `run_checks` retains actual combined output and failed/interrupted outcomes; it imposes no output cap. `_delivery_issue_context` (283–286) is only prompt text.

**Decision:** export submitted reports from their actual invocation boundary, including failed/rejected submissions and fixer summaries (add the missing summary at the existing return). Reuse check outcomes, focused checkpoint references and every review attempt. Add explicit predecessor/decision context where a retry or question currently loses it. Evidence filenames alone are insufficient: include the meaningful submitted report and relevant referenced evidence content while it is accessible; report unreadable evidence as a gap. Never scan arbitrary paths or credentials. Do not parse prose into accepted status. The reviewed result and owner acceptance are distinct fields.

**Check:** rejected first submission and later correction both survive; failed check output and final pass are separately available; missing referenced evidence cannot become confirmed complete delivery. Preserve existing required check, worker-authority and cumulative-review tests.

### R4 — GitHub comment delivery, independent readback and uncertain effects

**Inspected external primary source:** GitHub's official REST OpenAPI, revision
`c9c95fe34ced05fe076001f5c55704742bc8e7f8`, file
https://github.com/github/rest-api-description/blob/c9c95fe34ced05fe076001f5c55704742bc8e7f8/descriptions/api.github.com/api.github.com.json . Download SHA256 `6d9bbb20d8865b01464028937f2403954ad46598b4ebd3513dcb1a15b1a84aa7`; pinned and main downloads matched. Document info version 1.1.4, GitHub v3 REST API. Read-only `curl` succeeded; no repository mutation or authentication probe was needed for this documentation.

**Documented interface:** `POST /repos/{owner}/{repo}/issues/{issue_number}/comments` requires string `body`, returns 201 or explicit errors including 403/404/410/422. Description explicitly supports issues and PRs, warns that creation triggers notifications and rapid creation may cause secondary rate limiting. `GET /repos/{owner}/{repo}/issues/comments/{comment_id}` returns raw Markdown `body` by default. URLs: https://docs.github.com/rest/issues/comments#create-an-issue-comment and https://docs.github.com/rest/issues/comments#get-an-issue-comment . The inspected body schema supplies **no maxLength**. No numeric payload limit is asserted here.

**Installed consumer:** `gh --version` returned 2.23.0. Its actual `gh api --help` supports explicit `--hostname`, `--method`, JSON `--input -` and complete `--paginate`; flags with fields otherwise switch to POST. Use explicit methods and argument arrays, never interpolate evidence into shell. REST API version 2022-11-28 is the existing repository convention; this plan uses ordinary issue comments, not a new GraphQL dependency. Future target/auth capability still requires operation-boundary verification.

**Decision:** use a small deterministic publisher through installed `gh api`, defaulting to the delivery issue. Allow a known explicitly selected linked PR as destination; never create a PR. Serialize compact structured Markdown with full meaningful payloads, not full transcripts. Start with one body; if the consuming API explicitly rejects length with no effect, partition at sections/events and, when needed, lossless text continuations. Use its actual diagnostic/verified limit, not an invented cap. Other 422 errors are not length evidence. Rate/auth/network errors are reported, not automatic retry loops. No attachment service or local-only fallback.

Persist publication intent and part IDs/content digests in existing history before sending. Include a stable run/snapshot/part marker in each body. After send independently GET and compare actual body, target and identity. After uncertain send, paginate destination comments and read exact matching candidates before any retry. Match marker **and content**, not marker alone; ambiguity stops that publication. A complete destination scan with no matching effect permits a targeted retry under unchanged authority; incomplete reads do not. This is not a claim of server-side idempotency or exactly-once delivery. Finish reports success only when all parts and required discovery links are confirmed. Snapshot boundaries exclude publication bookkeeping itself.

**Alternatives:** overwrite issue body risks unrelated data; blind append risks duplicates; local attachment links fail after deletion; metadata-only Phoenix cannot carry this content. Reusing tracker mutation/readback semantics is smaller than a new delivery service.

**Check:** fake subprocess boundary exercises exact methods, bodies, readback mismatch, accepted-send/lost-response recovery, incomplete pagination, definite length rejection and multi-part readback without dropping text. Genuine scoped GitHub publication plus independent checkout-free retrieval is mandatory later; mocks do not prove it.

### R5 — Authority and linkage ownership

**Repository evidence:** [track-open-issue](../../skills/track-open-issue/SKILL.md#resolve-the-owner-and-authority) requires qualified target, usable gh/auth/read capability and actual target/operation write authority; reads or ADMIN are not authority. Its delivery path needs no candidate quality review. [finish-session](../../skills/finish-session/SKILL.md#issue-linked-delivery) separates reviewed implementation delivery from acceptance and closure. Existing launch authority has no GitHub-publication grant. [Planner](../../skills/planner/SKILL.md) currently permits safe planning without an issue; FR-013 intentionally changes that planned-artifact boundary, not bare runtime task intake.

**Decision:** final owner-approved execution handoff must explicitly include run-scoped publication to the qualified issue/selected PR and reciprocal linkage operations. Carry this scope as optional delivery authority in existing launch input/retained authority; the field conveys an actual grant, never creates one. Start/resume/finish reuse unchanged scope without a question every finish. Missing scope blocks only external effects and reports trace delivery deferred. This planning run grants no such scope. Do not add a startup gate for bare tasks, paid scope, worker permissions or GitHub availability.

Planner owns no-issue understanding/brainstorming, complete open/closed overlap discovery, exact reuse or authorized creation/readback/quality review before artifact production. User-requested creation, once actually scoped, needs no second routine consent. Existing issue #45 needs no creation. Finish/delivery owner ensures every known delivery PR links its issue, and issue discovers PR, independent of trace location; trace publisher verifies/reuses links and performs only granted missing link comments. No automatic close, reopen, labels, PR creation or issue-body replacement.

**Check:** no-issue positive create/reuse examples and missing target/auth/scope cases; PR/issue navigation from either entry; wrong target or missing permission causes zero writes and a concrete corrective action. Later live proof requires explicit target and effect authority.

Returned worker is not accepted result. Existing initial-plus-two task/session dispatch allowance remains an actual runtime constraint, not a new trace limit.

[Phoenix owner](../../docs/coordinate-implementation.md#local-phoenix-configuration) excludes prompts/responses/tool data/paths/errors. Keep that exporter and safe status projections unchanged. Only the explicitly authorized GitHub trace carries meaningful ordinary Q/A. Preserve credential exclusion at capture/export: do not copy bridge token, auth headers, environment/config dumps or credential files. Known credentials in otherwise needed content are excluded with an explicit gap; ordinary conversation is not suppressed. No claim of universal free-text secret detection, no sanitization agent or per-question review gate.

**Checks:** existing `test_tracing.py`, authority and historical-compatibility fixtures plus focused new credential sentinels at the GitHub payload boundary; prompts and permission tests demonstrate carrier behavior, not model obedience. Old runs remain readable with unavailable coverage; no historical backfill/conversion. Disable new publication/capture integration on rollback without deleting history or remote comments.

## Research disposition and risk selection

Reuse sufficient graph/SQLite and current skill evidence. Refresh only the consequential SDK owner-answer and GitHub interface gaps above. No new library, service or version choice is needed; installed capability versions are provenance, not admission requirements.

Select early permanent tests at **question hook → bridge → runner history** because silent loss/misattribution would invalidate every downstream trace. Select production publisher reconciliation tests before finish integration because remote effects cannot be safely inferred from a timeout. No disposable prototype or exhaustive replay is justified: both risks have existing production seams and bounded deterministic oracles. Hook availability was inspected, not exercised here. Schedule the genuine representative live run and checkout-independent GitHub readback at the earliest composed boundary with all producers and actual permission; unrun proof cannot release feature acceptance.

Remaining runtime uncertainties are test obligations, not assumed successes: installed hook result shape/order, terminal buffer drain under failure, actual target permission, API rejection details, and later evidence availability. If these disprove the proposed mechanism, correct the affected design and renew review/approval when requirements, scope or acceptance change. Material unresolved external policy must return to the owner; neither this research nor future field presence authorizes publication.
