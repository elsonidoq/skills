Overall executive brief

  • Goal: reduce avoidable questions and rework through better planning, then retain meaningful execution facts for later improvement after the worktree is gone.
  • Design gate: review this schematic, each component brief and these bullets; obtain explicit owner agreement before detailed plan production or continuation. Page creation, interaction, silence, no answer, cancellation or denial leaves the gate closed. Significant changes require renewed agreement.
  • Low overhead by design, not a speed claim: deterministic capture reuses existing tools, handoffs and the same workflow database. No manual coordinator logging, extra execution-time agent, new DB or service. Latency and runtime behavior are not measured here.
  • Durability: actual Q/A, worker resolutions, submitted proof, rejection reasons, validation outcomes and available code/commit/PR references go into GitHub, not just counts, hashes or disposable local paths.
  • Tradeoff: full meaningful content can require multiple comments and readback. Missing permission or uncertain delivery is reported separately from implementation outcome; inspect effects before retrying. Abrupt death can leave capture gaps.
  • Safety: retain actual credential protection and scoped external authority without routine Q/A publication approval. Keep the separate local metadata-only Phoenix exporter unchanged. No universal free-text secret-detection promise.
  • Assessment: owner-triggered, after completion, starting from an issue or PR; inspect supported later fixes and propose small changes, never autonomous skill edits or execution-time RCA.
  • Current approval: the owner's actual “ok I approve the plan. Start implementing” instruction approves the shown source/design/plan scope and local implementation after bounded alignment and parent inspection. Previous cancelled gates granted no consent. The later grant permits factual trace comments and independent readback on existing issue #45 only; no PR creation, push, new issue or closure is authorized. Required proof is not acceptance by approval. See the checklist for exact approved snapshot identities and scope.
  • Proof still needed later: real paired capture, complete durable readback, practical failure/recovery and assessment without the execution checkout. Static tests do not prove model obedience or live delivery.

Component brief reference

Planning + issue association
  • Purpose: understand the request; brainstorm with the owner only when needed.
  • Input → output: request and declared tracker → qualified issue and bounded scope.
  • Choice: reuse an exact overlap or create/read back the requested issue with actual scoped authority; no duplicate or automatic reopen.
  • Boundary: missing tracker capability, target or permission is an honest blocker, not a runtime fallback issue.
HTML design review
  • Purpose: make the high-level architecture understandable before detailed planning.
  • Input → output: current requirements and proposed boundaries → this clickable schematic, component briefs and overall executive bullets.
  • Choice: a small self-contained document, not a visualization service or framework.
  • Boundary: showing the page is not owner agreement; actual current source/design approval is recorded separately in the checklist.
OWNER DESIGN APPROVAL
  • Purpose: let the owner agree to the actual schematic and executive explanation before detailed plan production or continuation.
  • Input → output: reviewed current design → explicit owner agreement or a closed gate.
  • Boundary: cancellation, denial, silence or page interaction grants no consent. Significant design changes renew agreement.
  • Choice: this is distinct from requirements approval and final plan/tasks/implementation approval; no approval action is performed on this page.
Detailed plan + tasks
  • Purpose: derive interfaces, sequence and independently verifiable worker tasks after design agreement.
  • Input → output: approved source and high-level design → detailed plan and tasks with acceptance, completion evidence and real gates.
  • Boundary: the aligned plan/tasks carry this agreed gate; current approval covers the presented scope, not unverified implementation behavior or ungranted external effects.
  • Choice: reuse Standard/TinySpec processes and executor-sized contracts; ordinary technical choices remain autonomous.
FINAL IMPLEMENTATION APPROVAL
  • Purpose: authorize only the reviewed current plan/tasks and explicit implementation scope.
  • Input → output: current artifacts, review findings and proof limits → actual owner grant, or no launch.
  • Boundary: source/design agreement alone grants neither execution nor live GitHub effects. Previous cancelled questions were not consent.
  • Choice: external factual/link publication needs named target/operation scope; field presence or credentials do not create authority.
Execution tools + workers
  • Purpose: deliver approved tasks using the existing controller, SDK tools and worker handoffs.
  • Input → output: scoped task contracts → submissions, actual checks, checkpoints and independent review.
  • Proposed capture: automatically observe owner Q/A, worker resolutions, rejected completions, failures, inspected retries/escalations and meaningful proof.
  • Boundary: no manual coordinator log, extra execution-time RCA agent or blind retry; worker return is not acceptance.
Existing history — same SQLite DB
  • Purpose: retain ordered facts at the current execution boundaries, not add a new database.
  • Input → output: tool/handoff/check/review facts → attributable history with available run/task/worker/attempt identities and explicit gaps.
  • Choice: reuse history and review rows; distinguish actual owner answers from coordinator resolutions and pair by known identity.
  • Boundary: this design does not certify capture completeness; local implementation proof and final live acceptance are separate. Optional capture loss is reported; existing operational safety history stays required.
Finish / practical error publication
  • Purpose: move assessment-relevant facts out of the disposable worktree into GitHub.
  • Input → output: drained retained facts and scoped authority → compact structured full-meaning trace, counts, references and independently confirmed parts/links.
  • Choice: publish actual Q/A, meaningful submitted proof, rejection reasons and validation; no full transcript dump or metadata-only substitute.
  • Boundary: capture coverage and delivery status are separate from implementation outcome. Missing permissions, uncertain readback and abrupt-death gaps remain honest.
GitHub issue
  • Purpose: durable delivery entry and issue-led evidence discovery after worktree deletion.
  • Input → output: confirmed trace/link comments → actual factual evidence and discovery of every delivery PR.
  • Choice: default trace destination is the qualified issue; an explicitly selected linked PR can host it instead.
  • Boundary: no automatic closure, body overwrite or fallback issue. No remote write is authorized by this design page.
Linked PR
  • Purpose: provide PR-led access to the same associated delivery evidence and code references.
  • Input → output: known delivery PR → confirmed link to its qualified issue; the issue also discovers this PR.
  • Choice: every delivery PR links its issue even if trace content stays in the issue; reuse existing verified links.
  • Boundary: no PR creation or push. Late PR discovery establishes missing scoped links without blindly republishing the trace.
Owner-triggered assessment
  • Purpose: analyze failures and post-completion fixes afterward, not during execution.
  • Input → output: explicit issue OR PR URL, linked traces and supported code/commits/fixes → cited targeted improvement proposals.
  • Choice: distinguish reusable process weakness from issue-specific omitted requirements; separate supported causes, hypotheses and missing evidence.
  • Boundary: no old checkout identity/access needed; no autonomous investigations, skill edits, tracker changes or statistical evaluation.
One publication-only recovery CLI
  • Purpose: recover missing or uncertain trace delivery when retained facts and actual matching authority are available.
  • Input → output: retained snapshot/intent plus inspected remote effects → confirmed missing parts/links or actionable uncertainty.
  • Choice: one narrow CLI usable through normal shell; no separate service or attached recovery tool.
  • Boundary: never rerun workers, providers, checks, Git commits or graph execution to recover a log; lost facts cannot be reconstructed as success.
