## Approach and required behavior

Make the smallest coherent owner-led clarification, updating contradictions in consumers
rather than broadly rewriting skills or adding a meta-skill, planning system, artifact
chain, framework, scoring ledger or task quota. A one-task fix remains one coherent task
with its tests and operative docs; more complex work may legitimately need more. Separate
task production owns the actual decomposition; this source is not a work-unit checklist.

**Delivery boundaries.** Tasks describe meaningful delivery outcomes. Writing/running tests,
evidence capture, verification, review preparation and routine cleanup normally belong to
the outcome they support. A separate task requires an independently necessary deliverable,
a real producer-consumer prerequisite, permission/manual gate, resource/lifecycle boundary
or material context incompatibility. A workflow noun alone is insufficient.

**Proof before reliance, not prototype before everything.** Prefer permanent tests of the
actual production helper in the earliest coherent implementation task. Establish necessary
proof before downstream reliance; an earlier verified intra-task step can suffice. A focused
existing test that observes the risk needs no disposable prototype or duplicate implementation.
Keep independently verified prerequisite exceptions for genuinely unresolved architecture,
durability/security uncertainty, migration risk, paid/live resource boundaries and expensive
downstream reliance. Non-isolatable risks still need the necessary real-system check and
permission. Do not mechanically merge those outcomes or release reliance on failed/unrun
REQUIRED proof.

**Applicable proof and cleanup.** Run a shared applicable check once, preserving EVERY
REQUIRED criterion/item mapping, pass condition, permission/manual gate and evidence binding
for every consumer. Consumers inspect and use applicable findings/artifacts as implementation
reference and preserve behavior with production tests; a report-only link is insufficient.
Reuse a valid result across consumers after checking revision, environment and scope; rerun
invalidated evidence, not unchanged proof for ceremony. Retain proof through all applicable
consumers and production validation. Cleanup is conditional and owned: routine test teardown
stays with its test/task; separate cleanup needs actual resources or a consequential,
independently gated outcome, not hypothetical scaffolding. Real runtime cleanup behavior may
itself be a product delivery outcome. Failed proof retains disproof/limits and blocks affected
reliance; correct/replan and renew affected producing reviews/approvals, without weakening
criteria or treating unavailable permission as technical disproof.

**Preparation/review.** Planner briefs and both depth reviews challenge redundant splitting,
duplicate proof implementations, unnecessary artifact/report chains and disproportionate
checks, as well as coverage/dependencies. Preserve separate delegated artifact producers and
corrections, exact-content approvals, required independent reviews, task-local REQUIRED
verification, per-task [checkpoints](../../skills/memory-handling/references/task-commit-contract.md),
and authorized execution/profile routing. Coordinator/checkpoint contracts stay unchanged;
a verified contradiction there requires explicitly approved scope, not silent expansion.

### Generic evidence-only acceptance example

A settled indexing change preserves sequential capture, replaces dump processing with one-pass
indexing and inline validation, contains record errors while later independent records/chunks
continue, keeps full diagnostics private and readable progress bounded, accounts for skipped
and successful populations and publishes useful results. Reader opening, completion, status
and cleanup must not rescan dataset content. Both modes and the maintained invocation remain
supported. Real policy prerequisites and operative docs reconcile; deployment, production,
resources and jobs are not interrupted.

A workflow-noun decomposition can unnecessarily separate inventory/prototype, capture,
reader, modes, status, progress, composition, docs, final checks and disposable cleanup.
Illustrative delivery groupings instead combine a genuine prerequisite with affected intake;
capture/reader with permanent actual-filesystem tests; modes/accounting/publication;
status with certified evidence-preserving runtime cleanup; existing progress with maintained
invocation; operative docs; and focused composed verification with independent review.
These seven illustrative outcomes are neither a template, task list nor cap. They show how
supported work can combine without weakening genuine gates or independent review.

The critical adversarial oracle is a saved descriptor → rebuild → reader open → reset/verify
→ frame scan path that can hide a silent reread. Reader opening must perform **ZERO dataset
content reads before first consumption**; tests observe actual producer/operator stage
advancement and read/call counters, not labels claiming a stage occurred. This is acceptance
context for generic scenarios, not permission to implement an indexing system or modify any
external project. Only relevant portable fixtures belong in this repository.
