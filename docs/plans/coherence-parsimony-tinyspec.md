## Scope and proposed implementation shape

### One policy owner, short consumers, managed project copies

Create **`skills/planner/references/parsimony.md`** as the single reusable concise policy/template owner. Keep one clearly delimited project-copy fragment headed **Parsimony and Actionable Checks** in that file; other shared actors reference the owner rather than maintain alternate full rules. Place managed copies of the fragment in project instructions because a global link alone does not meet project distribution. Installation-resolved links may accompany a copy; no hard-coded installation/project path belongs in global text.

The fragment must carry these semantics in a handful of understandable principles, not a hidden protocol under umbrella labels:

- Start with the smallest working solution. A speculative concern is not automatically a requirement. Omit unnecessary optional behavior without asking about every imagined safeguard; surface only consequential unresolved trade-offs.
- New safeguards, limits or blockers need an explicit requirement, actual external/interface/platform constraint, or concrete material implementation risk. Serious exposed security/data-loss risk can justify cheap necessary protection before an incident. Preserve real budgets/platform limits; invent no thresholds.
- Account for availability loss, false blocking, recovery friction, interruption and maintenance, including legitimate behavior prevented. Unrequested shutdown, expiration, deletion, cleanup, throttling and spending/resource ceilings are out of scope by default. Observe/report by default where safe; do not substitute observation for necessary protection.
- Reuse SDK/tool/compiler/platform behavior; check the relevant boundary and repeat only when changed state can invalidate evidence. Return ordinary safe errors to the executor with actionable correction; stop affected continuation for concrete unsafe/invalid state. A file-read size error normally means a smaller/paginated read, not global uncertainty or a fatal workflow gate.
- Distinguish original requirements, necessary implementation choices with their basis, and optional hardening in existing fields. Agent assumptions are revisitable, not untouchable because an earlier plan made them REQUIRED. Existing binding approvals/acceptance change only through existing gates.
- Review unnecessary additions as well as omissions. Application/task acceptance proves the requested outcome; framework regression/internal proofs are not an application startup/admission ceremony. Preserve real tests, permissions and safety protections.

Likely consumer edits are `skills/planner/SKILL.md`, `skills/brainstorming/SKILL.md`, `skills/planning-brainstorming/SKILL.md`, `skills/tiny-spec/SKILL.md`, `skills/delegating-architectural-planning/SKILL.md` and `skills/task-generation/SKILL.md` (both adapters).
