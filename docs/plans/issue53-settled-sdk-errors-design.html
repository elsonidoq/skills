Executive summary

  • Goal: a worker SDK error that is provably settled must not block resume --recovery-action fresh|continue. Today every graph worker SDK error blocks every action.
  • Mechanism: the host, which alone sees the SDK session at error time, adds a settled attestation to its error record. The adapter omits the "effects are uncertain" text only when that attestation is present.
  • Settled means: (a) no session was created, or (b) the session is idle and has no pending question. In SDK 1.4.0, idle means no agent run is active, and tools run only inside an agent run.
  • Safety property kept: never redispatch with a live writer. Errors during an active run or a pending question get no attestation and stay blocked. Absent attestation (old host, unknown) stays blocked.
  • Normal checks still decide: once the gate passes, the existing invocation, HEAD, source, index, escalation and saved-session checks apply unchanged. No new gate; no check removed.
  • Why an addition is needed: the adapter cannot tell a settled error from an uncertain one; the existing error record has only message. Trade-off: one additive field on an existing record and a host-side observation, instead of fragile message-text matching.
  • Limits: local tests use fakes or SDK mocks; no live provider overflow is run. Detached background processes started by a tool are not detected (same as for a successful return).
  • Out of scope: bridge compaction (#18), the "host exited without a result" path, historical failure rows (no backfill), provider message-text matching.

Interfaces and compatibility

  • Host → adapter error record: additive settled field (exact name fixed in the detailed approach). Only the literal attested value counts.
  • Old adapter + new host: old adapters read only message; the extra field is ignored. Behavior unchanged.
  • New adapter + old host: no field → strict, as today.
  • Graph store / recovery: no schema change; the failed row stores the error text as today. The existing gate reads that text.
  • Dependencies: pi SDK AgentSession.isIdle and waitForIdle (verified in installed 1.4.0). No version pin.

Material risks

  • Wrong attestation could let a redispatch race a live writer. Mitigation: observe SDK state directly, strict default, tests for every strict case.
  • Detached processes from tools are not seen by isIdle. Same exposure as a normal successful return; existing effect checks still run. Proposed as an accepted limit.
  • SDK semantics change in a later release. Mitigation: host tests use the installed SDK where the existing suite does.
