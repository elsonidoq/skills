Acceptance run-and-fix stage — high-level design

Issue: github.com/elsonidoq/skills#56. Source: acceptance-run-fix-tinyspec.md (stage 1). Select a box to see its purpose, inputs and outputs, boundaries and choices.

Reused, no change Existing, changed New Owner gate (workflow approval, not data flow)

Schematic

1. Planning (before the run)

→ "Acceptance scenarios" or "No acceptance scenarios" + reason → brief line "Run-and-fix stage: ON (n) / OFF (reason)" → scenarios copied unchanged

2. Runner: intake and tasks

→ retained contract (scenarios immutable for the run) → all checkpoints done; scenarios present? → no scenarios: go straight to review (as today)

3. Acceptance run-and-fix stage (new controller graph)

→ "yes" only for declared live/paid/destructive effects → exit code + output; fail → one rerun → both failure outputs → hypothesis · evidence · classification → implementation defect only → changed paths → allowed changes + task checks → fix commit SHA → run again
Loop: run → (fail, confirmed) → diagnose → classify → fix → checkpoint → run, until pass, a stop path, or the bound (choice C2). Each step writes evidence first.

4. Evidence, review, escalation and visibility

→ failure outputs, diagnoses, fix commits → verdict on review_base..HEAD
← flaky, oracle defect, spec gap/scope, bound, no progress, invalid diagnosis ← stage rows and phase spans

Executive summary

  • Goal. Detect and correct "every task passed, but the feature does not work" before the independent final review, with a fixed code controller and agents only inside nodes.
  • Skip when no scenarios. The router enters the stage only when the retained contract has a scenario block. Without it, the graph goes from the last checkpoint to review on the same path as today (test A-SKIP).
  • Oracle protection. Scenarios live in the retained contract, which the runner compares on resume, so the run cannot change them. The oracle guard rejects fixer changes to declared oracle paths and the task file before any commit (A-ORACLE). An "oracle defect" classification escalates; it never goes to the fixer.
  • Scope stop. The fixer gets the existing repair scope text (original task contracts and owned paths). "Spec gap / scope" and any scope growth or paid/live/destructive need stop for the owner (A-SPEC-ESC).
  • Bounded termination. A fix-iteration count (recommended default 3, plan override) and a no-progress stop (same scenario, same exit code, identical output after a fix). An uncertain or failed agent call is never replayed (A-CAP, A-NOPROGRESS).
  • Flaky confirmation. Each failure runs once more before diagnosis. A failure that does not repeat is "environment/flaky": no diagnosis, no fix, never a pass. Recommended result: one owner question "rerun stage / stop" (A-FLAKY).
  • Run safety. Each scenario declares allowed effects; default isolated/local. Declared live, production-write, paid or destructive effects need the existing manual gate. Stage approval grants no such authority. The runner does not sandbox commands (A-SAFETY).
  • No-replay resume. Each run, diagnosis and fix writes a history row before and after the call, in the style of the existing dispatch reservations. Resume continues from settled rows and stops on an uncertain one (A-RESUME).
  • Evidence to review. Failure outputs (private files), diagnoses and attributed fix commits go into a new section of the existing reviewer brief. The review range already covers all commits since review_base (A-E2E, A-EVIDENCE).
  • Quiet iterations. Routine stage steps do not wake the parent. Only questions and terminal completion do (owner guidance, A-QUIET).

Limits and open choices

  • Command scenarios only (owner decision a). Agent-judged and owner-judged scenarios are out of scope.
  • Scenarios do not run again after a final-review repair (choice C6, recommended exclusion).
  • After an oracle defect or spec gap, the owner corrects through planning and starts a new run; a run cannot change its retained contract.
  • Open for the owner: C1 flaky result, C2 bound form and default, C3 no-progress signature. Routine (recommendations given in the source): C4 executors, C5 shape check location, C6–C8.
  • Tests use offline fake adapters and fixture projects. They prove runner logic, not live model behavior.
