Select a box (pointer, Enter or Space) to see its purpose, inputs/outputs, boundaries and choices.

→ ON + command, or OFF + reason → one brief line → approval starts the existing run → commits + check evidence

Inside the runner loop (reused): the check fails → the same worker gets the actual output and fixes → the runner reruns all checks → pass = focused commit (or no-change checkpoint). Same failure twice = stop. At most initial + two worker calls per session.

Executive summary

  • Goal: a plan that changes behavior checks, without an owner request, that the integrated feature works end to end before the final review.
  • Automatic: task generation adds the acceptance task by default. It depends on all other tasks in the plan, so it runs last.
  • Run and fix: the existing check loop gives the fix, the rerun, the focused commit and the stop on no progress. No runtime code changes.
  • Oracle protection: non-empty owned_paths without the command and scenario files block edit-tool writes to them. Shell writes are not blocked, so the check first runs git diff --quiet HEAD -- <scenario paths>.
  • Visibility: one line in the existing approval brief: "Acceptance task: ON (command …)" or "OFF (reason …)". No new question. The owner can change it at that approval.
  • Safety: live, production-write, paid or destructive effects stay under existing owner gates. Isolated/local resources are the default convention.
  • Limits (accepted): the fixing worker also diagnoses; no automatic flaky rerun; an oracle defect or spec gap is found only if the worker asks the owner; one worker call even when the check passes first time; a fix outside owned_paths is refused; the final-review fixer can change oracle files that an earlier task owned (the reviewer sees it); new untracked scenario files are not detected by git diff.
  • Tradeoff vs. the rejected design: no separate diagnoser, classifier or flaky rerun. Less protection against a wrong oracle, much less new machinery.
  • Open choices: C1 — state the ON/OFF intent once in the planner source guidance (recommended) or also in tiny-spec. C2 — no simplicity-review edit (recommended).
