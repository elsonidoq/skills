## Findings and smallest correction directions

1. **Retired admission protocol survives as application prerequisites.**
   `tasks.md:15–55` requires external authority catalogs, manifests, custody admission,
   parent bindings, launch/challenge/readiness receipts and action-scope streams.
   These conflict with the newer operative instructions. Remove obsolete requirements
   and their dependent work, rather than merely declaring their wrappers empty.
   Preserve genuine owner permissions, sole-writer ownership, task checks and review.

2. **A retired 15-second oracle drives an unnecessary workaround ecosystem.**
   Shared context at lines 23–25 and every REQUIRED check use `workflow.PythonAnswer`;
   longer scenarios become separate operator harnesses whose outputs require further
   binding/reobservation. Current operating guidance accepts ordinary commands instead.
   Use actual focused Python/browser/integration commands and normal cleanup. Do not
   preserve a hard deadline merely to retain the infrastructure built around it.
   Real integration evidence remains necessary; a framework limit is not a product goal.

3. **Dependency reproducibility has expanded into forensic environment custody.**
   T001/V2, T004/V2 and validation's pre-admitted-input recipe require frozen dependency
   trees, identity/hash revalidation, descriptor-to-quickstart-to-store bindings and
   hash-bound external source/build copies. Ordinary manifests/locks, approved existing
   dependencies and normal temporary build output may suffice under the trusted local
   operator model. Retain a special mechanism only for a concrete surviving constraint.
   Do not infer installation authority or discard legitimate supply-chain precautions.

4. **Obsolete review/wire ceilings remain application acceptance blockers.**
   Shared context line 19 and T004/V2 retain 120000/262144-byte guards and payload
   measurement. Current operating guidance describes ordinary SDK continuation and an
   uncapped transport. Remove obsolete blockers and compensating ceremony; first verify
   actual current consumers. Do not replace them with new universal size rules.

5. **Verification repeatedly attests the whole environment instead of the changed seam.**
   Multiple items recheck stores, config/source/receipt bindings, locks, inventories,
   tool identities and audit provenance. Classify each check by the failure it detects
   and the state change that invalidates its result. Reuse valid setup evidence;
   reader/mapping/privacy/browser checks should test their actual application boundary.
   Keep meaningful composed integration tests, not duplicate attestation chains.

6. **Own-build dogfooding is legitimate, but its proof protocol is overbound.**
   FR-017 and SC-006 explicitly require retrospective and subsequent live observation
   of the monitor's own build. Preserve that outcome unless the owner changes it.
   T004 additionally demands precise pin/checkpoint/receipt chains and separately bound
   observer artifacts. Test whether ordinary run identity, recorded history and focused
   observation suffice. Same-build timing is a real scheduling constraint; do not replace
   it silently with a different demonstration or invent busywork to keep the run alive.

7. **Engineering defaults have become rigid acceptance policy.**
   T001/V2 mandates 500ms snapshots/250ms busy budgets; the monitoring contract calls
   them initial engineering bounds. Short transactions address a real SQLite contention
   risk, but these exact values are not owner product targets. Separate tunable choices
   from acceptance: responsive observation, safe contention handling and unaffected writer
   progress. Review exact versions/environment/import restrictions similarly, distinguishing
   real interface/security constraints from restrictions inherited from retired tooling.

## Keep: not evidence of overengineering by itself

- The four coherent outcomes: reader/DTO, early usable viewer, faithful history/live
  behavior, then own-build evidence and operating documentation. Task count is not a quota.
- Left run list/one selected-run graph, understandable brief details, accessible history,
  honest statuses, null/zero/provenance semantics and no fabricated execution edges.
- Read-only SQLite access, parameterized queries, short transactions and no controller actions.
- Server-side data minimization, safe text rendering and appropriate loopback/origin defenses.
  Credentials/private transcripts are real exposed risks, not hypothetical hardening prompts.
- Focused real reader/writer and browser integration tests alongside deterministic mapping
  fixtures; meaningful test failure remains failure. This is not a request to delete tests.
- Explicit owner-selected execution profile, unrelated-work preservation, focused task
  checkpoints and fresh independent final review under the actual current workflow.

The 80/240-character presentation choices and every additional defense are not automatically
bugs. Assess material costs; do not turn this review into an inverse rule demanding removal
of all limits or security checks. Necessary protections can be justified before an incident.
