## Required behavior

**R1 — Known plan and lifecycle.** Show every known planned agent call before execution begins, including each task worker and the planned final independent review. Keep later calls visible while earlier work runs. Update the corresponding planned node when a call starts/finishes, without a duplicate call. Distinguish pending, running, successful and failed execution using color plus explicit words/legend; distinguish waiting/blocked only where recorded evidence supports it. Unknown/incomplete is explicit, not success. Once the run stops, remaining plans must not imply guaranteed future execution (for example, “Not started; run stopped”). Task progress/checkpoint completion is not call execution success.

**R2 — Actual expansion, identity and relationships.** Dynamically add fixing agents, subsequent reviews and corrective calls when actually scheduled or recorded. Never predict fixes/reviews from rejection alone. Preserve distinct retries, corrective calls, rejected reviews and execution history. Show meaningful declared dependencies separately from recorded execution/causal relationships. Missing, ambiguous or cyclic relations stay qualified rather than guessed. Review execution success is independent of acceptance: “Successfully returned; changes requested” is not an execution failure.

A scheduled fixing **round** is not itself an individual agent call: it can contain several prompts. Where only the round is known, expose a plain-language scheduled-round notice in Details/history, not a fabricated call or call endpoint. Add individual fixing nodes when exact individual-call evidence exists. Subsequent review appears only when its scheduling/dispatch is recorded, not whenever rejection occurs. This evidence boundary implements “known planned call,” not hypothetical expansion; if implementation discovers a material conflict with it, return that affected requirement for decision rather than fabricate identity.

**R3 — Human node labels.** Every task-associated node shows a useful task number/designation (for example, **Task 3** or **T003**), readable task title and agent role. Task numbers are not prohibited internal IDs. Repeated calls have understandable distinctions such as “Task 3 — Fix 1” or “Review 2,” not opaque identities. For arbitrary opaque task IDs, provide a stable source-order task number without changing the internal identity. Selecting a node exposes its task text and available metrics.

**R4 — Details and metrics.** Details briefly and clearly label task number, full task work text, role, current state, outcome, actionable safe findings and metrics as applicable. Expandable full task text is allowed; a truncated executive summary is not full task text. Use concise prose, not record/metadata dumps. Use labels such as **Input tokens**, **Output tokens**, **Cost**, **Duration** only when recorded data supports them. Clearly separate **This call**, **Task total**, **Overall run**, and any useful **Session total** context. Never substitute session totals for call/task spend or double count cumulative snapshots or already-included summary subsets. Preserve known subtotals, dispatch/interval coverage and incomplete-attribution qualifications in ordinary language. Unavailable facts are brief and honest. Full text for old runs without retained text is “Full task text not recorded,” never reconstructed from current files or labels.

**R5 — Presentation exclusions.** Do not display opaque invocation, session, branch, epoch, occurrence, run-reference or other internal IDs in graph labels or Details, including expandable sections. Do not relocate an ID dump to “technical references.” Do not display raw schema keys, dotted paths or enum values: forbidden examples include `Scope: invocation_interval`, `invocation 0f0fe3bff3274f9e8effd28100f349d4`, session/branch/epoch UUIDs and `[sdk_cumulative_counters.input]`. Translate needed scope/provenance to ordinary words such as “This call” or “Session total.” Remove redundant opaque banner IDs and history/expander dumps, while retaining useful typed history, findings and qualifications in readable form. Keep identities in code/data for matching, routing and attribution; preserve run navigation/history and internal API/URL identifiers, not delete routing keys or redesign navigation.

**Color proposal for combined approval, not previously approved:** grey pending, blue running, green successful, red failed, amber waiting/blocked; dark readable text and explicit state words/legend throughout. Unknown/incomplete uses neutral styling with distinct text. A rejecting reviewer that returned successfully remains execution-green, with its separate verdict visible. Exact colors remain subject to combined approval and later visual acceptance.
