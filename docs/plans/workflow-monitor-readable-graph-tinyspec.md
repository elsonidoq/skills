## Proposed deterministic presentation contract

### R1 — Backbone and ownership

For a complete selected-run plan, show **every declared task and every declared prerequisite edge**, including redundant/transitive declared edges and pending tasks. Never prune dependencies to reduce crossings or invent a linear dependency chain. Keep stable run-scoped task node identities across state changes. An edge means prerequisite → dependent, not execution order.

Visually group each individual task-scoped worker/fixing attempt under its recorded same-run task anchor, instead of showing plan and execution as unrelated peers. Use containment/alignment and a visible task header to communicate ownership; omit attachment arrows when that ownership is expressed. Task progress remains separate from each attempt's own outcome and acceptance. Do not merge repeated attempts or hide failed calls. Run-scoped reviewer/fixer calls with no recorded task ownership remain distinct in a visibly named run review/execution area, not assigned to a guessed task. Keep the declared **“Planned independent review — not an agent call”** definition distinct from actual reviewer calls; visually associate them as definition versus history without a fictional dependency/scheduling arrow. Unknown/dangling task ownership remains explicit unassigned recorded history, never an invented planned task.

### R2 — Edge inclusion and layout

Apply this policy by semantic relation, not by timestamp or proximity:

| Relation/evidence | Default graph | Supporting presentation |
| --- | --- | --- |
| Valid declared prerequisite | Always include | Prerequisite identity in selection/Details |
| Plan→attempt attachment / definition→review attachment | Omit arrow where grouping communicates ownership | Visible group/header and task/occurrence/definition refs in Details |
| Recorded execution sequence | Omit | Retain recorded order in Details/history; explicitly not causality |
| Confirmed stopping occurrence with recorded support relation | Include that stop and its support→stop edge when explaining the recorded run's current stop | State/error qualification in Details; successful parent stays green |
| Explicit actual review-triggered correction / chain relation | Include when explaining visible fixing work, using actual IDs and qualified relation | Preserve rejection, failed checks, correction/review outcomes/ranges in Details |
| Missing, unresolved, dangling or cyclic causal relation | No fabricated edge | Show existing unknown/unresolved/cyclic qualification and available history |

For the existing resolved cross-run declaration, preserve its existing qualified correction meaning; it is not proof of an exact internal review→fixer scheduling edge. T017's explicit actual execution relations, when present, supply that finer chain; do not upgrade the existing earliest-fixer ordering heuristic into explicit recorded causality. Chain check/checkpoint nodes actually required to explain correction are distinct recorded supporting nodes, not planned tasks. Recovered ordinary checks remain in Details/history unless needed by the explicit chain; no extra stopping node for an old recovered check.

**Derived review assumption:** retain all available explicit correction connections that explain visible fixing work, including completed corrections. This conservative initial policy preserves chain context/rejection history without a history toggle or recency heuristic; approval should consider clutter in the representative case. It is not an original owner requirement. No default completed-history deletion or hidden-failure rule is proposed.

Secondary stop/correction connections do not set main task-DAG ranks or reorder prerequisites. Lay out task/group footprints from prerequisite edges, place attempts/supporting review history within their owning areas, then overlay eligible secondary connections. This separates semantic selection from geometry; it does not require ELK compound cross-hierarchy routing. Exact nesting, dimensions and routing are derived mechanisms to validate, not settled external-library guarantees. Selection may emphasize/expose relevant supporting history, but must not remove planned prerequisites or hide failure facts, mutate recording, or refit/reorder the main graph merely to highlight an edge.

### R3 — Labels, states and degraded data

Task headers show recorded task ID plus a short distinguishable title, not identical “Task” labels. Use existing label/summary as available; if label is generic or just the ID, take a short summary excerpt, falling back to ID/explicit unknown title. Missing legacy IDs use the stable public ref as a qualified fallback, not a fabricated ID. Full text remains available as inert text in Details. Individual execution labels distinguish role and attempt/recorded identity within the owner group; show source run identity when expanding correction history.

Do not print “Declared prerequisite” repeatedly on every arrow. Use a concise relation legend and selected-edge Details/label; preserve edge semantic metadata even if its default visible label is absent. Show stop/correction type and qualification without repeated long labels crossing the graph.

Preserve complete-graph execution/acceptance semantics: green returned execution is not accepted work; rejection/check failure must remain inspectable without recoloring a successfully returned parent. Preserve waiting/running/unknown qualifications and planned progress, pending work, read freshness and paging-independent summaries.

If the plan is missing/invalid/partial, retain valid history and explicit **“Complete graph unavailable”**. Do not manufacture backbone/group ownership from current task files, sequence or partial history. Empty history with a valid plan still shows the entire plan and review definition; no recorded calls are invented. Unsupported stores/read errors remain unavailable/error, not successful empty runs. Existing credential protection, inert rendering, closed read-only HTTP/SQLite boundaries and current recorded-content visibility remain unchanged.
