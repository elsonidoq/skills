### Routine unresolved-issue lifecycle

1. Resolve explicit `[HOST/]OWNER/REPO` from project instructions/configuration and verified remote evidence. On conflicting/missing target, ask for the affected target only. Check usable `gh`, authentication and issue capability without printing tokens; no automatic installation or auth refresh. Missing capability/authority reports `issue tracking: UNAVAILABLE` or `deferred`, with the candidate/evidence/resumption in the session response, **not** a new persistent local tracker.
2. For a verified candidate, inspect likely overlaps across open **and closed** issues by problem, affected area and evidence, following all pages as needed. Never merge or reopen by title guess. Use stable repo-qualified URL/`HOST/OWNER/REPO#N` for native IDs; a bare `#N` or OI-N is insufficient across repositories. Issue body retains problem/category when supported, primary evidence, resumption, and uncertainty. Native GitHub state is canonical; don't maintain a contradictory active Markdown status.
3. Create only within current issue-write authority. For an exact existing match, report deduplicated or make a narrowly authorized update. Immediately re-read a target before update; preserve unknown body sections, comments/history, labels/assignees and unrelated state. Compare with inspected content; changed/ambiguous targets stop the affected overwrite with a corrective action to re-inspect/review. Do not promise atomic compare-and-swap from a read/check alone.
4. Completion requires evidence tied to the recorded problem and current authority; record that evidence and verify resulting closed state. An API success/worker return/test command success alone is not proof that the underlying problem is solved. Reopening likewise requires a verified recurrence/resumption basis and authorization. Never change unrelated issues. An authorized close that lacks outcome proof is reported separately, not as a verified fix.
5. Independent GET/readback validates the exact issue URL, problem/evidence/resumption and intended state. Report created/updated/deduplicated/deferred/not recorded and separately operation confirmation versus outcome verification. Readback failure leaves verification unknown; don't repeat a possibly successful mutation blindly. External-only operations create no empty Git commit; retained repository changes keep normal checkpoints.

### Historical import and mapping

Input is an explicit source repository identity, source path, pinned revision and historical Markdown, plus explicit destination GitHub repository. Skill is portable; this repository's baseline is only the representative acceptance input. Dry-run is the default and performs **zero external writes** (read-only lookup is allowed and disclosed). Preview renders exact proposed issue content/state/link changes, identity matches, conflicts/unmappable records and counts. Apply requires explicit authority for the named destination and scope; preparing the skill is not permission to run migration.

| Source | Destination / preservation rule |
| --- | --- |
| OI-N and heading | Human-visible historical identifier/title plus deterministic body marker containing source host/repo, normalized source path and OI ID. Store pinned revision and immutable original entry permalink separately. Stable identity does **not** include title or revision, so renamed entries/revised snapshots reconcile; identical OI-N in different repositories/paths does not collide. Reject duplicate identities in one source. |
| Status open/closed | Native GitHub state; original status verbatim in the historical source excerpt. Closed input stays closed after staged creation/close reconciliation; not silently imported open forever. No invented fix, actor, original timestamp or closure reason. Use REST `state_reason: null` for unspecified historical reason, validate readback in the gated proof; GitHub's new import timestamps are not original history. |
| Problem, Primary evidence, Resumption condition | Preserve full narrative, negations, verified uncertainty and source caveats. Body renders clear sections; retains original Markdown text/immutable source traceability as well as navigable transformed references. Don't turn resumption into task execution or permission. |
| Latest verification / unknown fields / history | Preserve verbatim in the imported body/source excerpt, maintaining order/meaning. Unknown status or structure that cannot be mapped safely is reported with source location and reason, never silently dropped/defaulted; unaffected valid records can be previewed, but no claim of complete migration. |
| Relative Markdown links | Resolve against source file directory at the **pinned source repo/revision**, retaining anchors and link text; e.g. `../runtime/...` becomes that source repository's immutable blob link, not destination-relative Markdown. Do not reinterpret inline code paths as working links or claim referenced files/logs exist. Keep original excerpt for fidelity. |
| Absolute GitHub #2 link / OI references | Keep absolute #2 URL unchanged; it is an existing issue, not the destination number for OI-4. Preserve OI references with source-qualified immutable links; after verified mapping, optional destination links can supplement them. Do not create parent/blocked-by relations or close #2. |

Keep one deterministic import marker on the GitHub issue itself; no mandatory local state DB. An optional static source→destination mapping/report is non-authoritative and cannot override GitHub state. Scan all destination issue pages with `state=all`, excluding pull requests, and inspect raw marker equality rather than relying on search indexing/title. One exact marker identifies a prior import; multiple matches are a conflict. Human-confirmed mapping to pre-existing issues requires an explicit preview/decision and preservation review, not automatic title-based adoption. In this repository existing issue #2 overlaps OI-4, so a future apply must surface that overlap and obtain a mapping choice; planning chooses neither merge nor duplicate creation on that owner's behalf.

Rerun of unchanged source/destination is no-op. If source content/revision changes or destination body/state diverges after import, show differences and stop the affected update for reconciliation rather than overwrite. In particular a later intentional GitHub close/reopen must not be reset by stale source state. Distinguish an unfinished import-owned close from later human activity using inspected marker/provenance and remote content; ambiguity needs review.

Creates are not transactional with subsequent closing/readback. Following a timeout, lost response, interruption or partial close, first reconcile by exact stable marker across the **complete open+closed listing**, then GET the candidate; resume only missing confirmed steps. A known-created originally closed record can finish its intended close after conflict checks. Failed auth, rate limit, pagination/readback or uncertain remote visibility is an actionable incomplete operation, not a safe retry signal. Do not blind-retry a POST. Keep successful partial results and report unresolved identities; no rollback by deleting created issues.

**Concurrency bound:** GitHub issue creation offers no demonstrated unique-source-key constraint here. Normal sequential/repeated imports with visible marker state are idempotent; simultaneous independent importers or indeterminate visibility cannot honestly guarantee exactly-once. Require one cooperating apply operator per destination/source for this import, not a repository-wide sole-writer rule or lock subsystem. Detect duplicate markers and stop affected records if overlap occurs. If absence after a lost response cannot be established confidently, defer that identity for remote inspection/owner resolution rather than claim an automatic duplicate-free retry. Ordinary concurrent GitHub edits are detected best-effort by read-before-write/readback, not atomically excluded.

- [Official REST Issues, “List repository issues”](https://docs.github.com/en/rest/issues/issues#list-repository-issues): results can include PRs; per_page max 100. **Constraint:** exclude `pull_request` objects and don't mistake page size for total coverage. **Check:** multi-page open/closed/PR fixture yields only exact issue identities; error on any missing page.
- Same official page, “Create an issue”, body parameters and response codes: title/body supported, creation returns 201, no create-state parameter, notifications/secondary rate limiting apply; permissions can silently drop optional labels/assignees. **Constraint:** create then reconcile closed state separately; no optional labels/projects/assignments/attachments needed, no blind retry. **Check:** interrupted-create/close tests and independent readback; respect actual rate-limit errors without inventing quotas.
- Same page, “Update an issue”, `state` / `state_reason`: open/closed and nullable reason; body is mutable. Installed [`gh issue close`](https://cli.github.com/manual/gh_issue_close) offers completed/not planned/duplicate, not null. **Constraint:** prefer explicit REST null reason for historical unspecified closures instead of inferring completed; preserve original account in body. **Check:** real gated readback establishes actual API behavior; if null cannot be preserved, stop that mapping and return the demonstrated alternative/impact for review, not silently weaken fidelity.
- Installed [`gh issue create`](https://cli.github.com/manual/gh_issue_create) / [`edit`](https://cli.github.com/manual/gh_issue_edit) help expose explicit repo/body-file and unrelated parent/blocking features. **Constraint:** explicit target and safely encoded body, no shell interpolation of Markdown, no attachment uploads/task relationships/auth refresh. **Check:** hostile Markdown/secret-sentinel and command-argument fixtures.
