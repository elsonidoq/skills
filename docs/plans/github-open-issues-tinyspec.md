### Routine unresolved-issue lifecycle

1. Resolve explicit `[HOST/]OWNER/REPO` from project instructions/configuration and verified remote evidence. On conflicting/missing target, ask for the affected target only. Check usable `gh`, host-qualified authentication and issue capability for that exact host/repository without printing tokens; no automatic installation or auth refresh. Missing capability/authority reports `issue tracking: UNAVAILABLE` or `deferred`, with the candidate/evidence/resumption in the session response, **not** a new persistent local tracker.
2. For a verified candidate, inspect likely overlaps across open **and closed** issues by problem, affected area and evidence, following all pages as needed. Never merge or reopen by title guess. Use stable repo-qualified URL/`HOST/OWNER/REPO#N` for native IDs; a bare `#N` or OI-N is insufficient across repositories. Issue body retains problem/category when supported, primary evidence, resumption, and uncertainty. Native GitHub state is canonical; don't maintain a contradictory active Markdown status.
3. Create only within current issue-write authority. For an exact existing match, report deduplicated or make a narrowly authorized update. Immediately re-read a target before update; preserve unknown body sections, comments/history, labels/assignees and unrelated state. Compare with inspected content; changed/ambiguous targets stop the affected overwrite with a corrective action to re-inspect/review. Do not promise atomic compare-and-swap from a read/check alone.
4. Completion requires evidence tied to the recorded problem and current authority; record that evidence and verify resulting closed state. An API success/worker return/test command success alone is not proof that the underlying problem is solved. Reopening likewise requires a verified recurrence/resumption basis and authorization. Never change unrelated issues. An authorized close that lacks outcome proof is reported separately, not as a verified fix.
5. Independent GET/readback validates the exact issue URL, problem/evidence/resumption and intended state. Report created/updated/deduplicated/deferred/not recorded and separately operation confirmation versus outcome verification. Readback failure leaves verification unknown; don't repeat a possibly successful mutation blindly. External-only operations create no empty Git commit; retained repository changes keep normal checkpoints.

Rerun of unchanged source/destination is no-op only with exact title/body/marker/provenance/native-state equality and the same independently verified native reason. No normalization may strip disclaimers, unknown sections, arbitrary human edits or reason changes to make equality pass. Compare against the reviewed render and retained verified observation in existing operational return/provenance, not a new database. A different reason, even another otherwise admissible value, needs reconciliation; absent prior reason evidence is not proof of unchanged history. If source content/revision or destination title/body/state/reason diverges, show differences and stop the affected update rather than overwrite. In particular a later intentional GitHub close/reopen must not be reset by stale source state. Only the exact import-owned pending body/title/marker with open state and null reason is eligible to resume its missing close after immediate GET/conflict checks; a final body later reopened, an edited pending body or ambiguous ownership is not. Same-valued intervening human actions cannot be excluded by content/readback alone; retain this best-effort limitation, not an atomic or historical-no-edits guarantee.

Creates are not transactional with subsequent closing/readback. Following a timeout, lost response, interruption or partial close, first reconcile by exact stable marker across the **complete open+closed listing**, then GET the candidate; resume only missing confirmed steps. A known-created originally closed record can finish its intended close after conflict checks. Failed auth, rate limit, pagination/readback or uncertain remote visibility is an actionable incomplete operation, not a safe retry signal. Do not blind-retry a POST. Keep successful partial results and report unresolved identities; no rollback by deleting created issues.

**Concurrency bound:** GitHub issue creation offers no demonstrated unique-source-key constraint here. Normal sequential/repeated imports with visible marker state are idempotent; simultaneous independent importers or indeterminate visibility cannot honestly guarantee exactly-once. Require one cooperating apply operator per destination/source for this import, not a repository-wide sole-writer rule or lock subsystem. Detect duplicate markers and stop affected records if overlap occurs. If absence after a lost response cannot be established confidently, defer that identity for remote inspection/owner resolution rather than claim an automatic duplicate-free retry. Ordinary concurrent GitHub edits are detected best-effort by read-before-write/readback, not atomically excluded.
