# Early technical risk reduction

## Authority and scope

Shared owner for planner, TinySpec, architectural planning and task generation. Apply
within existing stages and task fields, not a new workflow, schema or approval stage.
Verify this reference is readable; missing packaging stops affected planning with a
missing-install report. Direct/standalone callers verify their own preparation authority;
invocation does not grant execution. Planning schedules proofs, never executes them
without separate execution authority. Preserve existing TinySpec/Standard approvals,
REQUIRED mappings, task/evidence checkpoints and coordinator release gates.

## Select for leverage

Identify the hardest core or disproportionate technical uncertainty driving downstream
risk. Select early implementation proof only when it can be cheaply isolated with a
meaningful executable oracle and substantial downstream leverage. State the concrete
risk, expected value relative to effort, and justified selection or omission. No universal
cost threshold or obligatory prototype. Easy names/types/methods resolve by inspection
of source/documentation, not a script that prints them. Genuine architecture, durability,
security, migration, paid/live or expensive-downstream uncertainty retains its necessary
independently verified prerequisite and original gates. Non-isolatable uncertainty needs
real-system validation at the earliest feasible seam with actual prerequisites and
permission/capability gates, not a forced isolated script. Research alone is not an
implementation proof; apply the existing dependency research contract where relevant.

## Produce a minimal executable reference

Known bounded behavior normally uses permanent tests of the actual production helper, or a
verified earlier step inside its delivery task. Do not create a separate prototype task or
duplicate implementation when that proof suffices.

Use a disposable experiment only when one genuine consequential system, abstraction or
concept unknown is worth inexpensive proof before costly reliance. Ask ONE consequential
question; exercise the actual dependency or boundary with a meaningful, bounded observable
and applicable runtime/version, not production scaffolding. Use representative/adversarial
observations where they expose the unknown; a mock or trivial script that cannot observe it
is insufficient. The output is information: a conclusion/findings and tested limits, supported
by both script code and actual reproducible execution output. Include the minimal command,
observed result and applicability. Code without a run, or a failed/inconclusive result, cannot
prove behavior or release reliance on assumed success. In both task adapters,
mark the task title **[PROTOTYPE]** (or an explicit equivalent only if the observed format is
incompatible), and carry that marker and bounded informational scope into its handoff and
worker brief. Keep it tiny—typically 10/20/50 lines, or tens of lines, with clear observations
or a few direct assertions; this is guidance, not a hard cap. Do not add an accompanying proof
test suite or separate harness. If the real setup cannot stay cheap, expose the risk and use
the necessary validation layer rather than a dishonest probe. A pass establishes tested
bounds only, not general production correctness.

## Consume, validate, then clean up

Use a proof before reliance, but do not force a separate producer/consumer task chain. When
an independently necessary prototype prerequisite is a separate task, applicable consumers
depend on it and inspect/use its code, findings and still-applicable result. Otherwise place
the verified proof step before reliance within the same coherent task. Permanent production
acceptance tests remain necessary; a report-only link is not consumption. Reuse unchanged
proof only when revision, environment and scope still apply: run a shared check once with
every criterion/item mapping, pass condition, evidence binding and gate, and rerun only
invalidated proof where affected.

Retain proof through all applicable consumers and production validation. Only then safely
discard actual disposable material; keep concise command/result/limits in the existing
evidence owner, not an artifact/report chain. Routine teardown belongs inside its task.
A separate cleanup task needs a real independently consequential resource or outcome, not
hypothetical experiment cleanup. Discover project destinations; there is no fixed global
proof directory.

## Disproof and return

Failed/adversarial experiments block downstream reliance on the assumed approach. Retain
observed disproof and limits, diagnose the bounds, correct/replan the approach and affected
consumers, and renew affected existing producing reviews/approvals when source/specification,
scope, acceptance or dependencies change. Never label a failed technique proven, erase an
attempt, weaken criteria post hoc or blindly retry. Missing permission/capability is an
evidence gap, not technical disproof. Unrun experiments also cannot release assumed
dependents. Return exact gaps, blocked consumers and required correction/evidence through
existing gates; no automatic approval or separate experiment-approval workflow.

## Review and handoff

Both TinySpec and Standard reviews check justified selection/omission, executable criteria,
real-runtime applicability, any genuinely necessary producer/consumer dependency, proof
reuse and retention, production acceptance, disproof routing and feasibility/gates. Direct
tasking and standalone/helper-managed planning apply the same contract; neither assumes
planner already applied it. Keep a prototype informational, separate only an independently
necessary prerequisite, and leave normal tests, evidence and teardown inside coherent work.
Return the rationale, applicable dependencies, proof applicability/results/limits and blocked
reliance through existing source/task review and coordinator handoff. Static examples and
instruction tests demonstrate sensitivity only, not real-library or model-obedience proof.
