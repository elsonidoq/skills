# Early technical risk reduction

## Authority and scope

Shared owner for planner, TinySpec, architectural planning and task generation. Apply
within existing stages and task fields, not a new workflow, schema or approval stage.
Verify this reference is readable; missing packaging stops affected planning with a
missing-install report. Direct/standalone callers verify their own preparation authority;
invocation does not grant execution. Planning schedules proofs, never executes them
without separate execution authority. Preserve existing TinySpec/Standard approvals,
REQUIRED mappings, task/evidence checkpoints and coordinator release gates.

## Select for leverage

Identify the hardest core or disproportionate technical uncertainty driving downstream
risk. Select early implementation proof only when it can be cheaply isolated with a
meaningful executable oracle and substantial downstream leverage. State the concrete
risk, expected value relative to effort, and justified selection or omission. No universal
cost threshold or obligatory prototype. Easy names/types/methods resolve by inspection
of source/documentation, not a script that prints them. Non-isolatable uncertainty needs
real-system validation at the earliest feasible seam with actual prerequisites and
permission/capability gates, not a forced isolated script. Research alone is not an
implementation proof; apply the existing dependency research contract where relevant.

## Produce a minimal executable reference

Schedule an independently verifiable producer before plumbing/integration that assumes
its success. Build the smallest disposable script, program, test or benchmark exercising
the hard behavior, not production-quality abstractions. Use the real dependency/runtime
and applicable version where relevant; a mock or trivial script that cannot observe the
risk is not sufficient. Bound inputs/outputs and representative/adversarial assertions or
observables to the risk. Record objective success/failure criteria, reproducible commands,
expected evidence and capability/permission gates in existing task fields. Record commands
actually run, observed findings, dependency/runtime/revision applicability and limitations.
An unrun or unavailable REQUIRED check is NOT VERIFIED and cannot release dependents;
a pass establishes tested bounds only, not general production correctness.

## Consume, validate, then clean up

Retain executable artifact, commands and findings until all applicable production consumers
have consumed the reference and validated production behavior. Each production consumer
has an explicit earlier producer dependency and acceptance requiring it to inspect and run
the applicable proof, use it as the implementation reference, and preserve proven behavior
with production tests. Merely linking a report is not consumption. Include remaining
integration-risk checks, not just proof replay. Reuse requires still-applicable revisions,
dependency versions and environment; changes invalidate affected evidence.
Schedule cleanup only after all applicable consumers and production validation pass.
Disposable material need not become production plumbing; preserve reproducible evidence,
findings and limitations in the established evidence owner. Discover project destinations;
there is no fixed global proof directory.

## Disproof and return

Failed/adversarial experiments block downstream reliance on the assumed approach. Retain
observed disproof and limits, diagnose the bounds, correct/replan the approach and affected
consumers, and renew affected existing producing reviews/approvals when source/specification,
scope, acceptance or dependencies change. Never label a failed technique proven, erase an
attempt, weaken criteria post hoc or blindly retry. Missing permission/capability is an
evidence gap, not technical disproof. Unrun experiments also cannot release assumed
dependents. Return exact gaps, blocked consumers and required correction/evidence through
existing gates; no automatic approval or separate experiment-approval workflow.

## Review and handoff

Both TinySpec and Standard reviews check justified selection/omission, executable criteria,
real-runtime applicability, explicit production consumption/dependencies, retention through
all consumers, production tests before cleanup, disproof routing and feasibility/gates.
TinySpec carries approach and required evidence without embedding a task checklist;
Standard/helper carries sequencing/verification without replacing installed task production.
Direct TinySpec/tasking and standalone/helper-managed planning apply the same contract,
not an assumption that planner already applied it. Return risk rationale, producer → consumer
→ production validation → cleanup mapping, commands/evidence/applicability, limits and blocked
reliance into existing source/task review and coordinator handoff. Static examples and
instruction tests demonstrate sensitivity only, not real-library or model-obedience proof.
