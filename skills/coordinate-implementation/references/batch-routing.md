# Qualified batch routing seed

This global prior informs one profile per coherent sequential invocation, not per-task
assignments. It is provisional guidance, not a callable default, performance guarantee,
benchmark-only eligibility rule or universal quality/cost ranking. Task contracts and
owner decisions remain authoritative.

## Applicability to planning/advisory invocations

Planning/advisory consumers use the same six-factor assessment, independent family/effort
rationales, exact owner-selected profile and selection/observed/repair gates below, with their
own permissions and output verification. Assess applicable factors for the invocation rather
than invent implementation task IDs. Implementation-only batching, task-count and REQUIRED-item
rules do not become planning prerequisites. An explicit owner-mandated stage profile (Standard
`plan_create`: Sol with exactly medium supported effort for the entire direct/helper pass)
controls that stage; this seed cannot substitute another profile or create a family hierarchy.
Standalone helper selection remains separate and cannot bypass a manager-governed Standard rule.

## First proposal recipe

Start each first proposal with the actual invocation demands and verification boundaries.
Inspect all six factors below, name the concrete remaining work and weakest **adequate**
oracle, and record applicable approved guidance or explicit `none` with uncertainty.
Before comparing candidates, inspect only the retained evidence materially needed for that
comparison, or state explicit non-reliance/absence. Then compare plausible adequate
families and effort separately, and only then make a provisional proposal. This order
prevents post-hoc benchmark justification; it is not a broad evidence audit.

Each compact existing table row or brief must include: remaining work/weakest adequate
oracle; one plausible adequate alternative; the specific selection difference, or `no
established difference`; and the provisional choice or exact owner preference. Account
briefly for omitted plausible families. Do not enumerate variants, require equal rows or
use diversity as a reason. `Complex`, `safe`, `more margin`, benchmark-leader, or
cheapest/fastest claims are not comparisons. The objective is sufficient capability
without an unsupported premium, not a universal size, quality, or cost ladder.

**Compact example (after demands and explicit non-reliance):** “The remaining inference
is reconciling async settlement with cross-mode publication; the weakest adequate oracle
misses failure custody. Luna/medium and Sol/medium are plausible adequate alternatives;
there is **no established difference** between them for this invocation. Family: the oracle
gap identifies verification uncertainty, not a model deficit. Low and medium are supported,
but no additional remaining inference over low is established; retain the tie unless an exact
owner preference selects medium without claiming benefit.” A real tie or exact owner preference
is not a benchmark claim. This example does not rely on retained benchmark evidence.

## Assess all six factors

Record ordered task IDs and the weakest material condition, not an average across tasks.

| Factor | Inspect before proposing a profile |
| --- | --- |
| Residual reasoning | Compare closed design and implementation difficulty with remaining inference; ambiguity still requires an owner/design decision. |
| Agentic/tool depth | Tool-chain length, environment exploration, stateful interactions and long-horizon recovery. |
| Verification blind spots | REQUIRED contract strength, oracle quality, check cost and observability, manual gates and the weakest material unobservable failure; cheap reliable proof can offset moderate implementation complexity, never missing criteria. |
| Scope/coupling | Shared files/interfaces, producer/consumer checks, practical combined verification feasibility, attributable failures, integration reach and context fit. |
| Failure cost/reversibility | Blast radius, durable/security effects, rollback permission and cost of preserving/recovering valid work. |
| Applicable approved guidance | Exact relevant project guideline, applicability and evidence pointer, or explicit none with uncertainty. |

Read compact project guidance through the existing coordination lifecycle. With empty guidelines,
use this seed without inventing project success history. Relevant approved guidance may refine or
override the seed; it cannot override owner/source authority, permissions or REQUIRED gates.
Raw attempt outcomes are not approved guidance and never automatically mutate it.

## Provisional family and effort choices

Apply rubric first, capability verification second. Family and effort are independent dimensions:
record a comparative **Family rationale** and a separate **Effort rationale** for remaining inference.
Family explains sufficient capability versus the named adequate alternative; effort names the
concrete remaining inference relative to a lower supported effort. Extra effort has no asserted
empirical benefit unless evidence establishes it; otherwise say it is empirically unestablished.
Compare suitable options even with zero previous launches: explain the actual shortfall or select
the adequate candidate without an unsupported premium. Build the suitability shortlist across the rubric's family options, not a habitual two-family subset.
Briefly explain omissions of other plausible families. Do not enumerate every model variant or force diversity.
Prior launch success establishes availability, not superiority; pending readiness is not inadequacy.
Closed design, bounded tools, cheap reversible recovery and strong cheap oracles can positively
justify an adequate candidate without a premium. A stronger family must explain that candidate's
concrete shortfall under the weakest adequate oracle; suitability alone is not a comparison.
Effort needs its own sufficiency/extra-inference rationale, not a family-derived label. Model
variety is not itself a goal. When adequate candidates tie, preserve the uncertainty and let an
exact owner preference select one without a superiority claim.
Distinguish avoidable orchestration overhead from inherent reasoning; real stateful tooling/recovery still carries risk.
Effort respects a strict requirement versus a default preference: mandatory medium excludes low;
a default permitting low does not. Owner overrides retain the original proposal and reasons.
Neither dimension implies the other. These symbolic options are not provider bindings or
guaranteed supported pairs; there is no universal ladder.

| Family | Family rationale | Effort rationale |
| --- | --- | --- |
| Luna | Shallow, closed-design work with strong contracts, bounded tools and cheap recovery can justify Luna. | Choose any supported effort only for named remaining inference; family does not imply an effort. |
| Sol | Stronger reasoning or deeper tool use may justify Sol, subject to actual task blind spots and evidence. | Low can suffice when inference is tightly bounded; medium needs a separate remaining-inference rationale. |
| Astra | Consider Astra when its task-specific capability difference is established or an owner preference resolves an adequate tie. | Select supported effort independently; no fixed family-to-effort step follows. |
| Terra | Consider Terra on the same comparative basis, including a no-established-difference tie. | Select supported effort independently; no family ranking follows. |

Luna/max remains a symbolic supported effort only when it has an explicit extra-reasoning
rationale; max must remain recorded as max, never renamed medium. The family rows normalize
attention; they neither require equal proposal rows nor enumerate variants.

Moderate complexity with closed design and strong cheap reliable oracles can justify an adequate
symbolic proposal without a premium even while readiness is pending, with separate family/effort rationales. Weak oracle/hidden coupling
favors a justified stronger option only while contracts remain adequate; inadequate contracts
stop at producing review/renewal. Evaluate the weakest condition, not an average or score.

Deep tool use, weak oracles, unresolved architecture, high failure cost and relevant
repeated negative guidance defeat optimistic Luna routing. Propose a justified
stronger option only with adequate contracts; unresolved design stops at producing review/owner
clarification, never escalation. Otherwise stop at the owner/design gate; more effort cannot resolve missing
requirements, permissions or an inadequate verification contract. Do not bypass those gates
by substituting a model. Split only for material profile/context/permission/prerequisite
incompatibility, preserving order and producer verification before consumer work.

## Evidence limits

When benchmark signals materially support a comparison, inspect their underlying retained span
*after* demands/oracles and *before* the comparison/proposal. Identify exact family/version/effort,
harness and task relevance, retained provenance, and limits. Do not claim original-CSV inspection
unless it occurred. Unlike harnesses, compilation/evaluation dates, and missing snapshots are not
interchangeable; no row supplies Pi probabilities, causal effort gains, or a leaderboard choice.
Evidence absence/non-reliance is explicit and does not make a supported pair ineligible.

The [canonical feature research](../../../specs/002-batch-routing-contracts/research.md)
("Inspected representative signals and limits", "Runtime and ownership findings", Decisions
1–4) supplies provenance for this distilled prior, not project-specific learned policy.
Its SciCode non-agentic subproblems, AutomationBench-AA multi-turn environment, Terminal-Bench
4.0 mini-swe-agent tasks and small custom coding sample use different harnesses and versions.
Luna/max improvement does not equate it to Sol on difficult agentic work; Sol low/medium and
Astra/Terra signals do not create a universal ranking. Do not average unlike rows or infer
Pi success rates: snapshots and some verification are unknown; compilation time is not
an evaluation date. Benchmark absence does not prove a supported pair ineligible.

## Readiness before dispatch

Keep proposal, readiness/gaps, exact owner selection, historical launch and dispatch outcome
separate in the existing brief/table; no new score or ledger. A catalog-only candidate can remain
recommended while pending readiness. Dispatch needs the conjunction of:

- Applicable authoritative evidence of authenticated availability for the exact provider/id in
  the intended context. A catalog entry or credential presence alone is insufficient;
  missing/stale/opaque evidence is a precise gap, never a permissive default.
- Applicable authoritative runtime-supported choices include the exact selected effort.
  Thinking flags, suffix syntax and permissive missing-metadata defaults alone are insufficient.
  Unsupported effort, clamping or omitted/different effort blocks invocation. Reuse still-applicable proof;
  inspect provider mappings/source only for concrete uncertainty, contradiction, clamping risk or
  absent necessary support evidence, not a universal fresh audit.
- A current exact launch contract, permitted model scope/thinking ceiling, tool/extension access,
  mutation permissions, execution environment and exact owner selection agree with the profile.
  Parent availability does not prove a different detached-child environment ready. Unchanged
  applicable context/contract proof is reusable; resolved launch preparation may be the
  final preflight before provider invocation and no previous launch is required.

Use safe permitted passive evidence; these requirements do not assume a callable discovery API.
If verification is insufficient, surface the gap: stop affected dispatch, retain the recommendation
and ask for bounded authorization or an explicit fallback choice; never silently substitute Sol.
Inaccessible passive evidence asks, never speculative auth/configuration commands. Selection alone
never authorizes auth refresh, live discovery, provider probes or profile refresh. An explicit fallback
requires independent justification, its own readiness checks and exact owner selection.
Runtime-declared readiness is not live acceptance, quota/network health or model obedience.

## Selection and conditional repair gates

Record factors, applicable evidence or none, proposed versus owner-selected exact binding
and effort, independent rationales and a conditional repair option in the existing brief/tracker.
Verify permissions, tool access, callable binding and supported effort using the readiness conjunction
at assignment and dispatch. Copy the exact selected `model: "provider/id:effort"` unchanged into
actual arguments; settings/agent-default mismatch stops launch. Requested/selected is not observed;
unobservable actual model or effort stays unknown. An owner approval while readiness is pending
approves selection only, not dispatch or probes.

If verification fails, inspect the child run, invocation, partial commits and check evidence,
then diagnose capability versus planning/spec, contract, batching, environment/tooling,
external dependency or unknown. Preserve valid work and prior attempts. Conditional repair
may increase effort, change family or both only with usable permitted binding/support and
owner selection; unknown cause stops blind restart. Supply the original assessment/profile,
passed/failed items, current state and whole contract; rerun every invalidated item and reuse
only confirmed-valid evidence. Repair success alone does not prove model-only attribution.
Return factual attempt/check evidence in existing task/runtime conventions, not indexed run
records. Only explicit future-directed user feedback authorizes project-local guideline
changes under the shared feedback contract; no inferred learning or routine persistence.
