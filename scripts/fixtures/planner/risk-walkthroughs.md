# Illustrative risk selection walkthroughs — A, D, E

Offline expected planning examples only, not agent-produced plans or real-system experiments.
B/C producer/consumer task shapes are in risk-tiny-tasks.md and risk-standard-tasks.md.

## A — easy method name

Inspect the relevant version's source/documentation to resolve the name/type question.
No executable spike merely to print names/types. No numbered proof task: uncertainty is
answered by inspection, not a leverage-bearing semantic core. Evidence: inspected API span
and applicability. Gate: preparation authority only; no implementation performed.

## D — non-isolatable environment risk

Whole-environment failover is observable only with actual topology, credentials and fault
controls. Schedule real-system validation at the earliest feasible seam, not a forced
isolated script. Prerequisites: topology available, deployment fixture prepared, fault
controls and monitoring usable. Criterion: observed failover preserves acknowledged writes
and restores availability within source-defined bounds. Check: observed environment runner
and acknowledged-write/failover observables. Evidence: actual command/output, topology,
runtime/revision and limits. Gate: explicit environment/fault-operation permission and
available capabilities; unrun/unavailable REQUIRED validation remains NOT VERIFIED and
cannot release dependent production reliance. This example did not run a real-system check.

## E — disproof

Suppose adversarial proof output shows lost queued writes; expected zero loss fails.
Retain observed disproof, command, artifact, applicability and limits; failed technique
is not proven. Block the assumed T002 production approach, diagnose bounds and correct/replan
the affected downstream plan. Renew affected existing source/task reviews and approvals if
scope, acceptance or dependencies change. A corrected attempt retains the first failure;
no weaker criteria or blind retry. Missing capability is an evidence gap, not disproof.
Gate: no downstream release from failed/unrun proof; correction needs existing authority
and affected approval renewal. The hypothetical result is not an observed library failure.

## F — outcome boundaries and ordinary wiring

A proposed “deliver importer, public API and browser flow” milestone leaves three independently
testable interfaces unfinished together, so it is not independently acceptable: split it into
bounded importer, API and browser slices. Each slice accepts with completed predecessor contracts
and its own result, without unfinished downstream implementation. A settled multi-file local
change has no independent deliverable, prerequisite, gate, resource or material context boundary
between its accepted behaviors. Keep all acceptance, focused tests, evidence, operative
documentation and routine teardown in one coherent delivery task: no inventory, prototype,
composition, report or hypothetical-cleanup task. An ordinary established cross-system wiring
outcome also stays together when its existing focused test observes the actual value at the
consumer boundary and its relevant documentation remains with the change. A workflow noun or
task-count target is not a split reason. This scenario does not require splitting legitimate
wiring or combining work that has a real independent boundary.

## G — risky operations retain their gates

A migration, paid or live boundary that requires separate evidence keeps its independently
verified prerequisite and original permission/manual gate. A tiny symbolic fixture or an
informational prototype does not replace required migration, real-system or paid/live
validation. This example executes no migration or live operation and establishes no external
behavior.

## H — shared proof applicability and lifetime

If revision/environment/scope remain unchanged, run the shared applicable check once with
every criterion/item mapping, pass condition, evidence binding and gate. When a change
invalidates proof for only one consumer, rerun only invalidated proof for that affected scope
and keep unchanged applicable results. Retain proof until all applicable consumers and production validation
pass; then safely discard actual disposable material and retain concise command/result/limits
in existing evidence. Routine teardown stays inside the delivery; no separate cleanup task.
This is a symbolic reuse/disposal scenario, not a runtime result.

## I — review, investigate, then brief

Final TinySpec or Standard review records one material local prerequisite: **T014** needs the
existing local `fixture-port` interface before its worker uses it. Evidence: the checked-in
interface declaration was inspected; unknown: whether the fixture is enabled in this checkout.
Next action: coordinator preparation checks the local fixture configuration within routine authority.
It completes that investigation before T014 worker reliance, then briefs T014 with the usable
interface location, observed result, evidence limit and remaining no-live-service gate. A later
worker discovery receives the same investigate-then-brief treatment; unrelated T015 local-doc work
continues. This is an illustrative carrier order, not autonomous coordinator behavior.

## J — unavailable boundary and routine recovery

If T014 instead needs `credential-vault:read` for the operation “read the staging fixture secret,”
report that exact unavailable capability and operation; corrective action is grant
`credential-vault:read` or provide an approved local fixture. Only T014 waits; T015 continues.
A routine worker or reviewer early return first triggers inspection of its invocation, unfinished
scope, actual checks and retained effects. A known correctable cause uses supported history/resume
or same-head evidence reassessment with a targeted correction/evidence handoff; it does not repeat
an unchanged expensive failure or seek routine consent. Unknown cause, target drift, or an actual
paid/data/external/manual boundary stops the affected continuation with its corrective action.
